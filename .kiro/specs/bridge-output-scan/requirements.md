# Requirements Document

## Introduction

This is a speed change. Behaviour must not change.

`EmulatorBridge.advance()` in `src/engine/emulator-bridge.ts` (step 5 of the loop, about lines 402-415) looks at every Fixture pin after every instruction. For each digital output pin it calls `isAnalogPin`, checks `direction`, calls `_portMap.get`, `port.pinState` and `mapPinState`. Measured standalone by the user: avr8js alone runs `examples/crosswalk/fixed` at about 103M cycles/s. Through the bridge the same HEX runs at about 20M cycles/s (5 output pins). `examples/heartbeat/fixed` (1 output pin) runs at about 51M cycles/s through the bridge.

This spec covers two candidate changes to the output scan:

- Option A precomputes the digital output pins once in `_build`, so the hot loop does no `isAnalogPin`, no direction check and no `Map.get`.
- Option B is Option A plus a dirty flag. The scan is skipped unless something that can change an output pin's state happened since the last scan.

Option B is built only if the design shows that every path that can change a pin's state is covered. Before any edit to `emulator-bridge.ts`, a preservation baseline is recorded on the unchanged bridge and a replay test is added that passes on the unchanged bridge. Every change is then checked against that baseline and the committed suite. The committed suite is 58 files and 1002 tests, and it passes on the unchanged code (run 2026-11-15).

Tests are evidence, not proof. A passing preservation test shows the recorded cases match. It does not show that every HEX, Fixture and input event list matches.

## Glossary

- **EmulatorBridge**: The class in `src/engine/emulator-bridge.ts`. It is the only file in `src/` that imports avr8js.
- **Bridge_Result**: Everything an EmulatorBridge run gives back: the return value of `EmulatorBridge.create` (a bridge or a BridgeError), and for each `advance()` call the `AdvanceResult` fields `cyclesConsumed`, `outputEvents`, `appliedInputs`, `appliedAnalogInputs` and `diagnostics`, or the BridgeError it returns; plus `cycleCount` after each call.
- **Output_Scan**: Step 5 of the `advance()` loop. After each instruction and `cpu.tick()` it compares each digital output pin's state with the last value seen and emits an OutputEvent on a change.
- **Output_Edge**: One OutputEvent `{ signal, value, cycle }` emitted by the EmulatorBridge, including the cycle-0 snapshot events.
- **Digital_Output_Pin**: A Fixture pin that is not analog and has `direction` `"output"`.
- **Pin_State_Path**: Any code path in avr8js 0.21.1 (under `node_modules/avr8js`) that can change the value `AVRIOPort.pinState(bit)` returns for some bit. Examples: writes to PORTx, DDRx and PINx (a PINx write toggles PORTx), timer output-compare overrides set by the COM bits, any other peripheral pin override, and `setPin`.
  - Note: Pin_State_Path includes direct writes to `cpu.data` that bypass the write hooks, such as stack pushes and the XCH instruction's write to data[Z].
- **Path_Inventory**: The list of every Pin_State_Path, with file and line in the avr8js 0.21.1 source, and for each path whether an AVRIOPort listener fires. It lives in `design.md`.
- **Port_Listener**: A callback added with `AVRIOPort.addListener`.
- **Option_A**: The Output_Scan change that precomputes the Digital_Output_Pins in `_build` as `{ idx, port object, bit, signal }` entries in ascending Fixture pin-index order, so the hot loop does no `isAnalogPin` call, no direction check and no `Map.get`.
- **Option_B**: Option_A plus a Dirty_Flag. The Output_Scan runs only when the Dirty_Flag is set or an Uncovered_Path could be active.
- **Dirty_Flag**: A bridge-private boolean that is set by every Pin_State_Path a Port_Listener or another bridge hook covers, and cleared by the Output_Scan.
- **Uncovered_Path**: A Pin_State_Path on which no Port_Listener fires and which no other bridge hook observes.
- **PWM_Fixture**: The new directory `fixtures/pwm_out/`: the sketch `pwm_out.ino`, the Fixture `fixture.json`, and the `build/` outputs.
- **Preservation_Baseline**: The file `src/engine/__tests__/baselines/bridge-output-scan-preservation.json`, recorded from the unchanged EmulatorBridge.
- **Baseline_Case**: One entry in the Preservation_Baseline: a HEX path, a Fixture, a run length, a stored input event list, and the recorded Bridge_Result.
- **Baseline_Hash_File**: The file `.kiro/specs/bridge-output-scan/BASELINE-HASH.txt`. It holds the SHA-256 of the Preservation_Baseline from `Get-FileHash -Algorithm SHA256` and the local time the hash was taken.
- **Preservation_Test**: The new file `src/engine/__tests__/bridge-output-scan-preservation.test.ts`. It replays every Baseline_Case through the EmulatorBridge and compares the result exactly.
- **Recorder_Script**: A temporary script under `scripts/` whose name starts with `tmp-` and ends with `.ts`, used to record the baseline or measure speed. It is deleted after use.
- **Committed_Suite**: Every test file committed in the repo today, under `src/engine/__tests__/` and `tests/`, including the pinned literals in `tests/examples/`.
- **Check_List**: In order: the Preservation_Test, the full suite (`npx vitest --run`), `npm run typecheck`, `npm run guard`, `npm run build`, and `npm run bench:examples`.
- **Example_Run**: One run of an Example in `examples/` (crosswalk, garage, heartbeat), buggy or fixed build, with the event list that `buildEventList` returns for the Example's committed `fixture.json`, its meta `gremlinSet`, `runCycles` and `campaignSeed`, and a run index. This is the same call `runOne` makes.
- **Step_Plan**: The step sizes from `planTarget` in `src/engine/step-plan.ts` with `maxStepCycles` 160,000, as `runOne` uses them.
- **Rest_Events**: The cycle-0 events with gremlinId "rest" that `buildScriptedEvents` in `tests/examples/examples-support.ts` adds for every digital input with `restState` "active"; the crosswalk raw cases of `bench:examples` apply them.

## Requirements

### Requirement 1: Behaviour stays the same

**User Story:** As a maker who runs Hexorcist, I want the faster bridge to give exactly the same results as today, so that a seed, a trace or a replay I saved before the change still means the same thing.

#### Acceptance Criteria

1. WHEN the EmulatorBridge and the unchanged EmulatorBridge (`src/engine/emulator-bridge.ts` as it is before any Option_A or Option_B edit) each get the same HEX program, the same Fixture, the same `schedule()` calls in the same order and the same sequence of `advance(requestedCycles)` calls, THE EmulatorBridge SHALL put the same Output_Edges as the unchanged EmulatorBridge into each matching `AdvanceResult`: the same number of edges, in the same order, and on each edge the same `signal`, the same `value` (one of `0`, `1`, `"input"`) and the same integer `cycle`.
2. WHEN two or more Digital_Output_Pins change state after the same instruction and its `cpu.tick()`, THE EmulatorBridge SHALL emit their Output_Edges next to each other in the same `AdvanceResult`, all with the same `cycle`, in ascending Fixture pin-index order, and SHALL emit no Output_Edge for a Fixture pin that is not a Digital_Output_Pin.
3. WHEN the initial `advance()` call of a bridge returns an `AdvanceResult`, THE EmulatorBridge SHALL start its `outputEvents` with exactly one cycle-0 snapshot Output_Edge per Digital_Output_Pin, in ascending Fixture pin-index order, each with the same `value` as the unchanged EmulatorBridge gives it (`"input"` included), and SHALL put no snapshot Output_Edge into the result of any later `advance()` call.
4. WHEN the EmulatorBridge applies the input events of the run described in criterion 1, THE EmulatorBridge SHALL return the same `appliedInputs` and `appliedAnalogInputs` as the unchanged EmulatorBridge in each matching `AdvanceResult`: the same number of entries, in the same order, and on each entry the same `signal`, the same `value` or `analog`, the same `cycle` and the same `appliedCycle`.
5. WHEN the firmware in the run described in criterion 1 reads a floating input, THE EmulatorBridge SHALL return the same floating-input diagnostics as the unchanged EmulatorBridge in each matching `AdvanceResult`, with the same `kind`, `signal`, `cycle` and `register` on each entry, in the same order, and no diagnostic added, dropped or moved to a different `advance()` call.
6. WHEN an `advance()` call in the run described in criterion 1 returns, THE EmulatorBridge SHALL return the same integer `cyclesConsumed` as the unchanged EmulatorBridge for that call and SHALL report the same integer `cycleCount` right after that call.
7. IF the unchanged EmulatorBridge returns a BridgeError from `create`, `createWithTestHooks`, `advance`, `schedule` or `supports` at some call in the run described in criterion 1, THEN THE EmulatorBridge SHALL return a BridgeError at that same call with the same `kind`, the same `message` and the same values for every other field the unchanged EmulatorBridge sets (for example `signal`, `cycleCount`, `capability`), and SHALL return a BridgeError at no call where the unchanged EmulatorBridge returns none.
8. THE EmulatorBridge SHALL keep the names, parameter types and return types of `EmulatorBridge.create`, `EmulatorBridge.createWithTestHooks` and every member of `EmulatorBridgeInterface` (`advance`, `schedule`, `supports`, `clockHz`, `cycleCount`) as they are today, and SHALL keep the field names and field order of `OutputEvent`, `AdvanceResult`, `AppliedInputEvent`, `AppliedAnalogInputEvent`, `FloatingInputDiagnostic` and `BridgeError` as they are today.
9. WHEN the Committed_Suite runs with `npx vitest --run` after a change to the Output_Scan, THE Committed_Suite SHALL report all 1002 tests in its 58 test files as passed, with no test skipped that runs today, and `git diff --stat -- src/engine/__tests__ tests` SHALL show no change to any committed test file, so that violations, verdicts, traces and every pinned literal in `tests/examples/` stay as they are today.
10. THE EmulatorBridge SHALL express every `cycle`, `appliedCycle`, `cyclesConsumed` and `cycleCount` it returns as an integer count of CPU cycles, and `src/engine/emulator-bridge.ts` SHALL contain no call to `Math.random`, `Date.now`, `performance.now`, `setTimeout` or `setInterval`.

### Requirement 2: Inventory of pin-state paths

**User Story:** As the developer of the bridge, I want every way avr8js can change a pin's state listed with its source location, so that I can tell whether a skipped scan could miss an edge.

#### Acceptance Criteria

1. THE Path_Inventory SHALL list every Pin_State_Path found in the avr8js 0.21.1 source under `node_modules/avr8js` as one entry per code location, giving the file path relative to `node_modules/avr8js` and the line number of the code that changes the state `pinState` returns. All line numbers SHALL come from one avr8js build (ESM or CJS), and the Path_Inventory SHALL name that build.
2. THE Path_Inventory SHALL include an entry for each of these path classes: writes to PORTx; writes to DDRx; writes to PINx (which toggle PORTx); timer output-compare overrides selected by the COM bits for Timer0, Timer1 and Timer2; any other peripheral pin override present in the avr8js source; `AVRIOPort.setPin`; and direct data-array writes, meaning writes to `cpu.data` that bypass the write hooks. The direct data-array writes class SHALL cover at least the stack pushes from PUSH, CALL, RCALL, ICALL and interrupt entry, and the XCH write to data[Z]. Where a class has no matching code in the avr8js source, its entry SHALL say so.
3. THE Path_Inventory SHALL state yes or no for each Pin_State_Path on two points. The first is whether a Port_Listener fires when that path changes the state, citing the file and line of the listener call for yes, or stating "none" for no. The second is whether another bridge hook observes the path, naming the hook for yes.
4. THE Path_Inventory SHALL state, as yes or no for each Pin_State_Path, whether the EmulatorBridge constructs the peripheral that owns the path (today: ports B, C and D, Timer0, Timer1, Timer2 and the ADC). A path whose peripheral the EmulatorBridge does not construct SHALL still be listed.
5. THE Path_Inventory SHALL state, for each Uncovered_Path, the condition under which that path can change a Digital_Output_Pin's state, in terms of register bits or register values the bridge can read. Two examples: the COM bits of a timer channel whose pin is a Digital_Output_Pin, and, for direct data-array writes, a stack pointer or Z pointer value that addresses the PORTx, DDRx or PINx byte of a port holding a Digital_Output_Pin.
6. THE design document SHALL contain the Path_Inventory, a description of Option_A and a description of Option_B. It SHALL state yes or no on whether Option_B covers every Pin_State_Path. For each Pin_State_Path it SHALL name the means of coverage: a Port_Listener, a named bridge hook, or a per-instruction check of the condition from criterion 5. A path with no coverage SHALL be marked "not covered" with the reason.
7. IF the source does not show whether a Port_Listener fires on a Pin_State_Path or whether a bridge hook observes it, THEN THE Path_Inventory SHALL classify that path as an Uncovered_Path and state what could not be determined.
8. IF no condition in terms of bridge-readable register bits or values can be stated for an Uncovered_Path, THEN THE Path_Inventory SHALL mark that path as one Option_B cannot cover and give the reason.
9. THE Path_Inventory SHALL record how the Pin_State_Paths were found: the files searched and every search pattern used, including the patterns for direct writes to `cpu.data`, so that a second reader can repeat the search on the same avr8js build and get the same list of entries.

### Requirement 3: Option A, precomputed output pins

**User Story:** As a maker, I want the bridge to skip per-instruction lookups it can do once, so that campaigns finish sooner.

#### Acceptance Criteria

1. WHEN `_build` returns a bridge, THE EmulatorBridge SHALL hold a precomputed list with exactly one `{ idx, port, bit, signal }` entry per Digital_Output_Pin and no entry for any analog pin or any pin with `direction` `"input"`, where `idx` is the pin's index in `fixture.pins`, `port` is the same AVRIOPort object that `_portMap` holds for the pin's port letter, `bit` and `signal` equal the Fixture pin's `bit` and `signal`, and the entries are in ascending `idx` order; IF the Fixture has zero Digital_Output_Pins, THEN the list SHALL be empty.
2. WHERE Option_A is in place, THE EmulatorBridge SHALL leave the precomputed list unchanged after `_build` returns, with no entry added, removed, reordered or reassigned for the lifetime of the bridge.
3. WHERE Option_A is in place, WHEN the Output_Scan runs after an instruction and `cpu.tick()`, THE EmulatorBridge SHALL iterate only over the precomputed list, read each pin's state with `entry.port.pinState(entry.bit)`, compare and update the pin shadow at `entry.idx`, and emit any Output_Edge with `entry.signal`, with no `isAnalogPin` call, no `direction` read, no `_portMap.get` call and no `_fixture.pins` access inside the step-5 loop of `advance()`, as shown by reading that loop in `src/engine/emulator-bridge.ts`.
4. THE EmulatorBridge SHALL build the precomputed list only after the HEX parse, `validateFixture` and `validateEvents` have all returned no error, and building the list SHALL neither throw nor return a BridgeError, so that for every input where `create` or `createWithTestHooks` returns a BridgeError today, it returns a BridgeError with the same `kind` and `message`, from the same check (HEX parse, then Fixture validation, then input-event validation).
5. WHEN the Option_A edits to `emulator-bridge.ts` are complete, THE developer SHALL run the Check_List in order, and SHALL count Option_A as passing only if the Preservation_Test matches all 41 Baseline_Cases exactly, `npx vitest --run` reports zero failed tests across the Committed_Suite and the Preservation_Test, and `npm run typecheck`, `npm run guard`, `npm run build` and `npm run bench:examples` each exit with code 0. No minimum speed-up is a pass condition.
6. IF any Check_List item fails under Option_A, or the Preservation_Test reports a difference from the Preservation_Baseline in any Baseline_Case, THEN the developer SHALL run no further Check_List item and record each item not run as "not run", restore `src/engine/emulator-bridge.ts` to its exact pre-edit content (the SHA-256 from `Get-FileHash -Algorithm SHA256` taken before any Option_A edit and the one taken after the restore SHALL be equal), keep the Preservation_Baseline, the Baseline_Hash_File and the Preservation_Test unchanged, skip Option_B, and stop and report the failing item, its output, and for a Preservation_Test failure the Baseline_Case and the earliest field that differs.
7. THE developer SHALL NOT edit, weaken, skip or delete the Preservation_Test, the Preservation_Baseline, the Baseline_Hash_File or any Committed_Suite file to make a Check_List item pass under Option_A.

### Requirement 4: Option B, skip the scan when nothing changed

**User Story:** As a maker, I want the bridge to skip the output scan when no output pin could have changed, so that long runs with few edges finish sooner.

#### Acceptance Criteria

1. WHERE the design shows that every Pin_State_Path in the Path_Inventory is covered, and names for each Pin_State_Path which cover applies (a Port_Listener, another named bridge hook, or a per-instruction check of the condition from Requirement 2.5), THE developer SHALL build Option_B on top of Option_A. One permitted per-instruction check is this: after every instruction, compare the DDRx byte in `cpu.data` of each port that has at least one Digital_Output_Pin with the value recorded at the last Output_Scan. This check covers the Uncovered_Path where a direct `cpu.data` write (for example a stack push or XCH) changes a DDRx byte with no Port_Listener call.
2. IF the design shows a Pin_State_Path that no Port_Listener, bridge hook or per-instruction check covers, THEN the developer SHALL skip Option_B, keep Option_A, and state in the report the uncovered path's file and line from the Path_Inventory and the reason it cannot be covered.
3. WHEN a Pin_State_Path covered by a Port_Listener or another bridge hook fires during an instruction or its `cpu.tick()`, THE EmulatorBridge SHALL set the Dirty_Flag before the Output_Scan point of that same instruction boundary.
4. WHEN an instruction and its `cpu.tick()` complete and the per-instruction check condition for an Uncovered_Path holds, THE EmulatorBridge SHALL run the Output_Scan at that instruction boundary. For the DDRx path, the condition holds when the DDRx byte of a port with at least one Digital_Output_Pin differs from the value recorded at the last Output_Scan, or from the value recorded when `_build` returned if no Output_Scan has run yet.
5. WHEN the Output_Scan runs under Option_B, THE EmulatorBridge SHALL clear the Dirty_Flag, SHALL record the current DDRx byte of each port with at least one Digital_Output_Pin for the check in criterion 4, and SHALL emit each Output_Edge with the same `signal`, `value` and `cycle` as the unchanged EmulatorBridge, in ascending Fixture pin-index order.
6. WHEN an input event is applied through `setPin`, or a test-hook listener from `createWithTestHooks` is called, THE EmulatorBridge SHALL set the Dirty_Flag before the next Output_Scan point. The only exception is an event or call that the design shows, citing the Path_Inventory entry, cannot change any Digital_Output_Pin's mapped value (`1`, `0` or `"input"`).
7. WHEN Option_B is in place, THE developer SHALL run the Check_List in order. THE Preservation_Test SHALL match every Baseline_Case with exact equality, and every other Check_List item SHALL exit with code 0.
8. IF Option_B differs from the Preservation_Baseline in any Baseline_Case, or any Check_List item exits with a non-zero code under Option_B, THEN the developer SHALL restore `emulator-bridge.ts` to the Option_A version that passed Requirement 3.5, run the Check_List again in order, continue with Option_A, and state in the report the failing Check_List item, or the Baseline_Case and the earliest differing field.
9. WHEN an instruction and its `cpu.tick()` complete while the Dirty_Flag is clear and no per-instruction check condition from criterion 4 holds, THE EmulatorBridge SHALL skip the Output_Scan at that instruction boundary, emit no Output_Edge for it, and keep the last-seen value of every Digital_Output_Pin unchanged.
10. IF any Check_List item fails on the restored Option_A after the fallback in criterion 8, THEN the developer SHALL undo every Option_A edit to `emulator-bridge.ts`, keep the Preservation_Baseline, the Baseline_Hash_File and the Preservation_Test, and stop and report the failing item and its output.

### Requirement 5: PWM fixture

**User Story:** As the developer of the bridge, I want a sketch whose output pins are driven by timer PWM and by plain writes, so that the baseline covers the timer-override path as well as the PORT path.

#### Acceptance Criteria

1. THE PWM_Fixture SHALL contain the sketch `fixtures/pwm_out/pwm_out.ino`, which in `setup()` sets PD6 (Arduino D6, Timer0 channel A), PB1 (Arduino D9, Timer1 channel A) and PB5 (Arduino D13) to output with `pinMode` and writes PB5 LOW, then in `loop()` calls `analogWrite` on PD6 and on PB1 and toggles PB5 with `digitalWrite` every 100 ms (1,600,000 cycles at 16 MHz), and reads no input pin.
2. WHEN 50 ms (800,000 cycles at 16 MHz) have passed since the previous duty change, THE sketch `pwm_out.ino` SHALL move PD6 and PB1 together to the next step of the authored sequence in choice C3. The sketch SHALL apply step index 0 (PD6 duty 0, PB1 duty 255) in `setup()` and SHALL wrap from step index 4 back to step index 0, so the five-step sequence repeats every 250 ms.
3. THE sketch `pwm_out.ino` SHALL contain the string "ATmega328P" at least once, SHALL contain no occurrence of "Arduino" in any letter case and no whole word "Uno" in any letter case, and SHALL hold only code and comments written new for this spec, with no third-party product or company names.
4. THE PWM_Fixture SHALL contain `fixtures/pwm_out/fixture.json` in the `{ "pins": [ ... ] }` shape of `examples/*/fixture.json`, with exactly the 3 pins of choice C12 in that order, each pin giving only `signal`, `port`, `bit` and `direction`. `validateFixture` SHALL return `null` for the Fixture the file holds.
5. WHEN the command `arduino-cli compile -b arduino:avr:uno --output-dir fixtures/pwm_out/build fixtures/pwm_out` is run, THE PWM_Fixture SHALL compile with exit code 0.
6. WHEN the compile command in criterion 5 exits with code 0, THE developer SHALL delete every file in `fixtures/pwm_out/build/` other than `pwm_out.ino.eep`, `pwm_out.ino.elf`, `pwm_out.ino.hex`, `pwm_out.ino.with_bootloader.bin` and `pwm_out.ino.with_bootloader.hex`, so that the directory holds exactly those 5 files, the same set `fixtures/analog_read/build/` holds.
7. IF the compile command in criterion 5 exits with a non-zero code, or cannot be run because `arduino-cli` or the `arduino:avr` core is not installed, THEN the developer SHALL stop, report the command output and exit code, install nothing, and make no further change.
8. THE developer SHALL leave every existing file under `fixtures/` and `examples/` unchanged, so that `git diff --stat -- fixtures examples` lists no changed file.
9. WHEN the pwm_out Baseline_Case is recorded, THE Preservation_Baseline SHALL contain, for `PWM_A` and for `PWM_B` separately, at least 10 pairs of consecutive Output_Edges on that signal whose `cycle` values differ by fewer than 100,000 cycles (6.25 ms at 16 MHz). This bound is well under the 800,000-cycle duty-step interval, so edges caused only by duty changes cannot meet it.
10. WHEN the pwm_out Baseline_Case is recorded, THE Preservation_Baseline SHALL contain at least 9 Output_Edges on `LED` after the cycle-0 snapshot event, and every pair of consecutive `LED` Output_Edges after that snapshot SHALL have `cycle` values between 1,568,000 and 1,632,000 cycles apart (100 ms ± 2 ms at 16 MHz).
11. IF the pwm_out Baseline_Case does not meet criterion 10, THEN the developer SHALL stop before writing the Baseline_Hash_File, report the recorded `LED` edge cycles, and make no further change.
12. IF the pwm_out Baseline_Case does not meet criterion 9 for `PWM_A` or for `PWM_B`, THEN the developer SHALL report which signal falls short and that the PWM_Fixture does not exercise the timer-override path, SHALL keep the pwm_out Baseline_Case in the Preservation_Baseline, SHALL NOT build Option_B, and SHALL continue with Option_A.

### Requirement 6: Preservation baseline

**User Story:** As the developer of the bridge, I want the current bridge's results recorded before I touch it, so that any change can be compared against a fixed record.

#### Acceptance Criteria

1. WHILE `src/engine/emulator-bridge.ts` has no uncommitted change and the PWM_Fixture of Requirement 5 has compiled, THE developer SHALL record the Preservation_Baseline, write the Baseline_Hash_File and add the Preservation_Test, and SHALL finish all three before any edit to `src/engine/emulator-bridge.ts`.
2. THE Preservation_Baseline SHALL contain 24 Baseline_Cases, one for each Example_Run of crosswalk, garage and heartbeat, buggy and fixed, with run indices 0, 1, 2 and 3. Each case SHALL store the event list that `buildEventList` returns for that Example_Run. Each case SHALL be replayed to the Example's `meta.runCycles` with the Step_Plan, without stopping at a violation. The cases SHALL be stored in the order crosswalk, garage, heartbeat; within an Example, buggy before fixed; within a build, run index ascending.
3. THE Preservation_Baseline SHALL contain 8 Baseline_Cases for `fixtures/blink_button/build/blink_button.ino.hex` with the Fixture of choice C9, and 8 Baseline_Cases for `fixtures/analog_read/build/analog_read.ino.hex` with the inline Fixture of choice C1 and no `restLevel`. Each case SHALL be run to 8,000,000 cycles with the Step_Plan. Blink_button case k SHALL hold the k-th list drawn and analog_read case k SHALL hold the (8 + k)-th list drawn, for k from 0 to 7, all drawn from one PRNG per choices C4 and C8. Each list SHALL hold 1 to 40 events with integer cycles from 0 to 7,999,999 in ascending order.
4. ### Requirement 7: Preservation test

**User Story:** As the developer of the bridge, I want a test that replays every recorded case and compares it exactly, so that a change in any edge, cycle or applied input fails loudly.

Each test SHALL use the HEX file at the stored path relative to the repo root, the stored Fixture and the stored input event list, SHALL step with the Step_Plan to the stored run length, and SHALL NOT stop at a violation.
2. WHEN a Baseline_Case is replayed, THE Preservation_Test SHALL compare each field stored in Requirement 6.5 with exact equality. The comparison SHALL cover the number of `advance()` calls, the `cyclesConsumed` of each call, all Output_Edges, all `appliedInputs`, all `appliedAnalogInputs`, all diagnostics and the end `cycleCount`.

The failure SHALL report the case's HEX path and its index in the Preservation_Baseline, the earliest field that differs, the list index of the first entry that differs, the expected value and the actual value. "Earliest field" means the earliest in the field order of Requirement 6.5, and within a list the lowest index.
4. THE Preservation_Test SHALL read the stored input event lists from the Preservation_Baseline without changing them. It SHALL NOT regenerate them with `createPrng` or `buildEventList`, and SHALL NOT write to the Preservation_Baseline or the Baseline_Hash_File.
5. THE Preservation_Test SHALL set an explicit per-test timeout in milliseconds in its own file. The value SHALL be fixed before any edit to `emulator-bridge.ts` and SHALL stay unchanged when Option_A or Option_B is checked.

7. WHEN the Preservation_Test file is run alone with `npx vitest --run` on the unchanged EmulatorBridge, THE Preservation_Test SHALL report 41 passed tests, 0 failed tests and 0 skipped tests, and the command SHALL exit with code 0.
8. IF the Preservation_Test fails on the unchanged EmulatorBridge, THEN the developer SHALL stop and report the failing case, the differing field, the expected value and the actual value.
