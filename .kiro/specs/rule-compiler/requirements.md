# Requirements Document

## Introduction

The Rule_Compiler turns a fixed set of plain-English Rule templates into a versioned JSON IR, and compiles a Rule_Set written in that IR into one deterministic `Checker` (the type in `src/engine/checker.ts`) for the gremlin-engine Campaign (`createCampaign`, `runCampaign` and `runSlice` in `src/engine/campaign.ts`). The Campaign verdict stays the job of the existing `computeVerdict` in `src/engine/verdict.ts`. This spec adds one optional input to `computeVerdict` for rules whose trigger never happened, and adds no second verdict function and no new verdict string. It also adds one optional field to `CampaignConfig` so the Campaign can pass that input (Requirement 13, criterion 2).

This spec is additive to the `emulator-bridge`, `input-pullup` and `gremlin-engine` specs and to the current code in `src/engine/`. It keeps their rules: the EmulatorBridge is the only module that imports avr8js, replay is a fresh emulator plus the same HEX, Fixture and ordered event list (no snapshots), simulated time is integer CPU cycles, there is no `Date.now`, `performance.now`, `setTimeout` or `Math.random` in engine code, and the Checker contains no AI and makes no network calls. The Rule_Compiler draws no random values. Test evidence from this spec is evidence, not proof.

Scope: this spec builds the IR, the Renderer, the Sentence_Parser, the IR_Reader and IR_Writer, the Rules_File_Reader, the compiler, the Trigger_Evaluator, the `computeVerdict` extension, the Campaign wiring, the Campaign_Config_Builder, and the spike wrapper. It does not build the UI chip builder or a CLI entry point; those later consume the Renderer, the Rules_File_Reader and the Campaign_Config_Builder.

Facts from the current code that these requirements rely on. Each is to be quoted from the source in `design.md`:

- F1. Cycle-0 output snapshot. `EmulatorBridge._build` builds one `OutputEvent` with `cycle: 0` for every output pin, whose value can be `"input"` (`src/engine/emulator-bridge.ts`, step 9, near line 264). `advance()` prepends that snapshot to the `outputEvents` of its initial call (near line 358). `runOne` passes that Step's `outputEvents` in the `stepIndex` 0 observation (`src/engine/campaign.ts`, near line 222). So the `stepIndex` 0 observation carries the snapshot.
- F2. Applied inputs. Every `AppliedInput` entry carries `appliedCycle` and the `gremlinId` copied from the scheduled event. Rest_Events carry `gremlinId` `"rest"`.
- F3. Step straddling. In an observation with `cycle` X that is not end-of-run, output events have `cycle` ≤ X, and applied inputs have `appliedCycle` ≤ X − 1, because the bridge applies inputs before it executes an instruction. An input applied at cycle X appears in the next observation. Data for one cycle can therefore arrive in two observations.
- F4. Run_Result contents. `RunResult` records `eventList`, `appliedInputs` (digital and analog merged, in application order), `outputEvents` (including the snapshot), `diagnostics`, `cannotCheck`, `violation` and `endCycle` (`src/engine/types.ts`).
- F5. Verdict today. `computeVerdict` returns `BROKE` when any Run has a Violation; otherwise it returns `COULDN'T TELL` when any Run carries a `CannotCheck`, when `unmappedSignals` is not empty, when fewer than `requestedRuns` Runs completed, or when no Gremlin produced an event; otherwise `HELD`. The Campaign fills `unmappedSignals` from `CampaignConfig.checkerSignals` and passes `unsupportedPeripherals: []`.
- F6. No run length in the observation. `CheckerObservation` carries neither Run_Cycles nor the Fixture. A Checker learns the run length only from `observation.cycle` at the end-of-run call, which equals `endCycle` and can be a few cycles above Run_Cycles.
- F7. Outcome validation. `callChecker` in `campaign.ts` turns a Violation with an empty `rule`, a non-integer or negative `cycle`, or a `cycle` above `observation.cycle` into a `checker-error`.
- F8. Floating diagnostics. `Diagnostic` is `FloatingInputDiagnostic` (`kind: "floating-input"`, `signal`, `cycle`, `register`) in `src/engine/types.ts`. The EmulatorBridge emits one only for a digital Fixture pin with `direction: "input"`, at most once per signal per bridge (`emulator-bridge.ts`, step 11b). Fixture `signal` strings are not checked by `validateFixture`.

Process constraints carried into design and tasks (Requirement 17 states them as requirements): `design.md` quotes the real types from `checker.ts`, `campaign.ts`, `verdict.ts`, `fixture.ts` and `types.ts` and does not restate them from memory; `design.md` names the exact arithmetic method for Window_Cycles; committed tests, baselines and fixture files are never edited; new tests go in new files; when a task writes a baseline file, work stops after that task so the user can commit; nothing is committed by the agent; acceptance tests written by the user are never changed or weakened to make them pass; no code is written until the user approves `tasks.md`.

## Glossary

- **Rule_Compiler**: The new TypeScript engine code under `src/engine/` that reads, renders, parses and compiles Rules. It imports no avr8js.
- **Rule_Compiler wiring function**: The Rule_Compiler function of Requirement 13, criterion 1 that takes a Rule_Set and a Fixture and returns the `checker`, the `checkerSignals` and the bound Untriggered_Rule function for `CampaignConfig`.
- **Campaign_Config_Builder**: The Rule_Compiler function of Requirement 13, criterion 10 that takes one Rule_Set, one Fixture and the other `CampaignConfig` fields and returns a complete `CampaignConfig` built from that one Fixture.
- **Rule**: One IR object of one Rule_Form.
- **Rule_Form**: One of `never`, `respond`, `count`, `hold`, `notLongerThan`.
- **Rule_Set**: The ordered list of 1 to 32 Rules given to the compiler. Rule_Set order breaks ties.
- **IR**: The JSON document `{ "version": 1, "rules": [...] }` defined in Requirement 1.
- **IR_Version**: The integer in the IR `version` field. This spec defines version 1.
- **IR_Reader**: The function that reads IR JSON text and returns a Rule_Set or Reasons.
- **IR_Writer**: The function that writes a Rule_Set as IR JSON text.
- **Condition**: An IR object `eq`, `above`, `below`, `all` or `any`, evaluated on a Settled_State.
- **Edge**: An IR object `rise` or `fall` over a Condition.
- **Signal_Name**: The `signal` string of a Condition. It names a Fixture pin by its `signal`.
- **BANNED_WORDS**: The exported list of words in `src/engine/copy-rules.ts` that user-visible text must not contain. This document does not write the words out.
- **Duration_Ms**: A duration field of a Rule, in milliseconds.
- **Clock_Rate**: `fixture.clockHz` when it is neither `undefined` nor `null`, otherwise 16,000,000 (Requirement 5, criterion 2).
- **Window_Cycles**: A Duration_Ms converted to CPU cycles by Requirement 5.
- **Canonical_Sentence**: The one English sentence the Renderer gives for a Rule (Requirement 2).
- **Renderer**: The function `render(rule)` that returns the Canonical_Sentence.
- **Sentence_Parser**: The function `parse(sentence)` that returns a Rule or a Reason.
- **Allowed_Character**: A character x is allowed at position P of an input when the leading P characters of the input followed by x form a prefix of the Canonical_Sentence of some valid Rule. The end of the text is allowed at P when the leading P characters are themselves a Canonical_Sentence (Requirement 3, criterion 9).
- **Rules_File**: A text file that holds either IR JSON or Canonical_Sentences, one per line.
- **Rules_File_Reader**: The function that reads the text of a Rules_File and returns a Rule_Set or Reasons.
- **Reason**: A plain-language string of 1 to 200 characters that says why input was rejected or a rule could not be checked.
- **Rule_Checker**: The `Checker` the compiler returns for a Rule_Set.
- **Rule_Monitor**: The per-Rule state machine inside the Rule_Checker.
- **Active_Rule**: A Rule with no compile-time `CannotCheck` (Requirements 5 and 6).
- **Reference_Evaluator**: A test-only, full-trace evaluator written separately from the Rule_Monitor and the Trigger_Evaluator, used as the oracle in Properties 4, 7 and 8.
- **Prefix_Oracle**: A test-only function, written separately from the Sentence_Parser, that says whether a string is a prefix of the Canonical_Sentence of some valid Rule. Property 9 uses it.
- **Trigger**: The event that gives a Rule something to check in one Run, counted only when the Rule's window fits in that Run (Requirement 12, criterion 1).
- **Trigger_Evaluator**: The pure function that says whether a Rule's Trigger occurred in one `RunResult`.
- **Untriggered_Rule**: An Active_Rule whose Trigger occurred in no completed Run of the Campaign.
- **Untriggered_Rule function**: The pure Rule_Compiler function of Requirement 12, criterion 3 that returns the Canonical_Sentences of the Untriggered_Rules for a list of completed `RunResult`s.
- **Run_Count_Phrase**: For a count N of completed Runs, the text `1 run` when N is 1, and the text `N runs` (N in decimal digits) for every other N, including 0.
- **computeVerdict function**: The existing function `computeVerdict(input: VerdictInput): Verdict | null` in `src/engine/verdict.ts` (fact F5), extended by Requirement 12, criterion 4.
- **Output_Pin**: A digital Fixture pin with `direction: "output"`.
- **Fixture**: The pin map fixture data checked by `validateFixture` in `src/engine/fixture.ts`.
- **Floating_Diagnostic**: An entry of an observation's `diagnostics` with `kind` `"floating-input"` whose `signal` equals the `signal` of at least one Digital_Input in the Fixture (fact F8).
- **CannotCheck**: An entry `{ rule, reason }` that a Checker returns in `cannotCheck`, or a compile-time mark of the same shape that the Rule_Compiler attaches to a Rule.
- **Gremlin_Engine**, **Gremlin**, **Gremlin_Set**, **Checker**, **Violation**, **Digital_Input**, **Analog_Input**, **Active_Level**, **Rest_State**, **Rest_Event**, **Rest_Level**, **Run**, **Run_Index**, **Run_Cycles**, **Step**, **Slice**, **Campaign**, **Run_Result**, **Verdict**: As defined in the `gremlin-engine` spec.
- **Inactive_Level**: For a Digital_Input, 1 when the Active_Level is `"low"` or absent, and 0 when it is `"high"`.
- **Initial_State**: The value of every referenced signal before any non-Rest_Event change, defined in Requirement 7.
- **Settled_State(c)**: The value of every referenced signal after every change at cycles ≤ c, defined in Requirement 8.
- **Application_Order**: The order in which the Rule_Checker receives changes and diagnostics: list order within one observation's `appliedInputs`, `outputEvents` or `diagnostics`, and call order across the observations of one Run.
- **Final_Cycle**: A cycle whose Settled_State can no longer change in the current Run (Requirement 10, criteria 3 and 10).
- **Occurrence**: A cycle at which an Edge happens (Requirement 8, criterion 5).
- **agent**: The AI coding assistant that carries out the tasks of this spec.
- **committed file**: A file that `git ls-files` lists at the start of a task (Requirement 17, criteria 1 and 9).
- **baseline file**: A committed file under `src/engine/__tests__/baselines/`, or a file that a task in `tasks.md` names as a baseline (Requirement 17, criteria 1 and 4).
- **committed fixture file**: A committed file under `fixtures/` (Requirement 17, criterion 1).

## Requirements

### Requirement 1: Versioned JSON IR

**User Story:** As a maker, I want rules stored in a small versioned JSON format, so that a rules file means the same thing in the browser and on the command line.

#### Acceptance Criteria

1. THE IR SHALL be a JSON object with exactly the fields `version` (the integer 1) and `rules` (an array of 1 to 32 Rules), and no other field.
2. THE IR SHALL define the Conditions `{ "op": "eq", "signal": S, "value": v }` with v equal to 0 or 1, `{ "op": "above", "signal": S, "value": n }` with n an integer from 0 to 1022, `{ "op": "below", "signal": S, "value": n }` with n an integer from 1 to 1023, and `{ "op": "all", "of": [...] }` and `{ "op": "any", "of": [...] }` with 2 to 8 Conditions in `of`. These ranges leave out `above` 1023 and `below` 0, which no ADC value from 0 to 1023 can make true.
3. THE IR SHALL limit Condition nesting to a depth of 4, where an `eq`, `above` or `below` Condition has depth 1 and an `all` or `any` Condition has a depth one greater than its deepest member.
4. THE IR SHALL define the Edges `{ "op": "rise", "of": C }` and `{ "op": "fall", "of": C }`, where C is a Condition.
5. THE IR SHALL define the Rules `{ "form": "never", "condition": C }`, `{ "form": "respond", "trigger": E, "withinMs": d, "expect": C }`, `{ "form": "count", "edge": E, "windowMs": d, "max": k }`, `{ "form": "hold", "after": E, "durationMs": d, "expect": C }` and `{ "form": "notLongerThan", "condition": C, "ms": d }`, where E is an Edge, d is a Duration_Ms, k is an integer from 0 to 65,535, and an integer field accepts any JSON number whose parsed value is an integer, whatever its text form (`1`, `1.0` and `1e0` are all the integer 1), except negative zero: an integer field whose parsed value is `-0` (for example `-0` or `-0.0`) is out of range, and THE IR_Reader SHALL reject it with a Reason that names its JSON path, so that round trips are exact.
6. THE IR SHALL accept as a Duration_Ms a JSON number greater than 0 whose digits from ECMAScript Number-to-String conversion, written out in plain positional notation with any exponent expanded, have an integer part of at most 9,999,999 and at most 7 digits after the decimal point, and THE IR_Reader SHALL judge the parsed number and not its JSON text form, so that `300`, `300.0` and `3e2` give the same Duration_Ms, `0.0000625` and `0.0000001` are accepted, and `0.00000001` and `10000000` are rejected.
7. THE IR SHALL accept as a Signal_Name a string that matches `^[A-Za-z][A-Za-z0-9_]{0,31}$`, is neither `all` nor `any`, and is not equal, ignoring case, to any entry of BANNED_WORDS, and THE IR_Reader SHALL reject a Signal_Name equal to such an entry with a Reason that names its JSON path. A Signal_Name holds only letters, digits and `_`, so a BANNED_WORDS entry can match it as a whole word (by the matcher of Requirement 15, criterion 8) only when the entry equals the whole Signal_Name.
8. IF the top-level value is a JSON object whose `version` field is absent or is not the integer 1, THEN THE IR_Reader SHALL return exactly one Reason that states that `version` is absent or names the JSON type of the value found (number, string, boolean, null, array or object), together with the number written by ECMAScript Number-to-String conversion when the value is a number, and SHALL return no Rule. The Reason SHALL copy no string value from the input.
9. IF the top-level value is not a JSON object, or any IR object has a missing field, a field not listed in criteria 1 to 5, a value of the wrong JSON type, or a value outside its stated range, THEN THE IR_Reader SHALL return one or more Reasons, at most one per offending value, each naming the JSON path of its offending value as field names from criteria 1 to 5 and zero-based array indexes from the document root (for example `rules[2].trigger.of.value`), and SHALL return no Rule from that document. For a field not listed in criteria 1 to 5, the Reason SHALL name the JSON path of the object that holds the field and state that the object has a field that is not allowed, with one Reason per such object.
10. IF the IR text is not valid JSON, THEN THE IR_Reader SHALL return exactly one Reason stating that the text is not valid JSON and SHALL return no Rule.
11. IF two or more Rules in one Rule_Set have the same Canonical_Sentence, THEN THE IR_Reader SHALL return one Reason per repeated sentence that names the repeated sentence (cut to fit the 200-character Reason limit) and the zero-based indexes in `rules` of every Rule that has it, and SHALL return no Rule.
12. WHEN the IR_Writer is given a valid Rule_Set, THE IR_Writer SHALL write it as IR JSON text with `version` 1, holding only the fields of criteria 1 to 5 and the Rules in Rule_Set order, and SHALL return the same text each time it is given the same Rule_Set.
13. FOR ALL valid Rule_Sets (Rule_Sets that meet criteria 1 to 7 and have no two Rules with the same Canonical_Sentence), reading the IR_Writer output with the IR_Reader SHALL give a Rule_Set deep-equal to the original (round trip).
14. THE IR_Reader SHALL apply the checks of criteria 10, 8, 9 and 11 in that order, SHALL return only the Reasons of the earliest check whose condition holds, and SHALL return without throwing for every input string.
15. WHEN the IR_Reader is given text that fails none of the checks of criteria 8 to 11, THE IR_Reader SHALL return the Rule_Set with its Rules in the order of the `rules` array and no Reason.
16. IF the IR_Writer is given a value that is not a valid Rule_Set, THEN THE IR_Writer SHALL return a Reason in place of IR JSON text and SHALL return without throwing.
17. THE IR_Reader and the IR_Writer SHALL build every Reason only from fixed wording, field names listed in criteria 1 to 5, array indexes, JSON type names, numbers, and the Canonical_Sentences of criterion 11, and SHALL copy no other string value and no field name not listed in criteria 1 to 5 from their input.

### Requirement 2: Canonical Sentence Templates

**User Story:** As a student, I want each rule to read as one plain English sentence, so that I can tell exactly what is being checked.

#### Acceptance Criteria

1. THE Renderer SHALL render the Conditions as follows: `eq` as `S is v`; `above` as `S is above n`; `below` as `S is below n`; `all` as `all of (C1, C2, ...)`; `any` as `any of (C1, C2, ...)`. S is the Signal_Name exactly as written in the IR, with its letter case kept. v and n are written as criterion 4 states. Each member of `all` and `any` is rendered by this criterion, at any nesting depth, in IR order, with members separated by one comma and one space. No space follows `(` and no space comes before `)`.
2. THE Renderer SHALL render `rise(C)` as `C becomes true` and `fall(C)` as `C becomes false`, where C is rendered by criterion 1.
3. THE Renderer SHALL render the Rules as follows: `never` as `C must never happen.`; `respond` as `Within d ms after E, C must be true.`; `count` as `E may happen at most k times in any d ms.`; `hold` as `After E, C must stay true for d ms.`; `notLongerThan` as `C must never last d ms or longer.`. C is rendered by criterion 1, E by criterion 2, and k and d by criterion 4. The `count` template uses `time` in place of `times` when k is 1 and `times` for every other k, including 0. Every template writes `ms` after d for every Duration_Ms, including 1.
4. THE Renderer SHALL write each integer (v, n and k) in decimal digits with no sign, no digit-group separator and no leading zero, with the integer zero written as `0`. THE Renderer SHALL write each Duration_Ms as the decimal value given by ECMAScript Number-to-String conversion, expanded out of exponent form, with no sign, no exponent, no digit-group separator, no leading zero in the integer part other than a lone `0`, no trailing zero after the decimal point, and no decimal point when the value is an integer. For example, 300 is written `300`, 0.1 is written `0.1`, and 5e-7 is written `0.0000005`.
5. THE Renderer SHALL produce each Canonical_Sentence from printable ASCII characters only. The sentence SHALL contain no space other than the single spaces shown in the templates of criteria 1 to 3, and no tab, CR, LF or other whitespace character. Its last character SHALL be one period, and its only other periods SHALL be decimal points inside Duration_Ms values. It SHALL have no leading or trailing whitespace.
6. THE Renderer SHALL compute the Canonical_Sentence from the Rule alone, independent of any Fixture, Clock_Rate, object key order or earlier call. It SHALL return identical strings for any two deep-equal Rules and SHALL leave the Rule it is given unmodified.
7. IF the Renderer is given a value that is not a valid Rule under Requirement 1, criteria 2 to 7, THEN THE Renderer SHALL return a Reason of 1 to 200 characters that names the JSON path of the offending value from the Rule root, written as Requirement 1, criterion 9 states (for a field not listed in Requirement 1, criteria 2 to 5, the path of the object that holds it), SHALL copy no string value and no unlisted field name from the value, and SHALL return no Canonical_Sentence. The result SHALL let a caller tell a Reason from a Canonical_Sentence without reading the text. The Renderer SHALL return without throwing for any JavaScript value, including `null`, `undefined`, an array, an object with a missing or extra field, a Duration_Ms that is 0, negative, `NaN` or `Infinity`, a Duration_Ms with more than 7 digits after the decimal point (such as 0.30000000000000004), and a Condition nested deeper than depth 4.
8. THE Renderer SHALL render the Rule `notLongerThan(eq(LED, 1), 300)` as `LED is 1 must never last 300 ms or longer.`
9. THE Renderer SHALL render the Rule `never(all(eq(A, 1), any(above(P, 100), eq(B, 0))))` as `all of (A is 1, any of (P is above 100, B is 0)) must never happen.`
10. THE Renderer SHALL render the Rule `count(rise(eq(BUTTON, 0)), 1000, 1)` as `BUTTON is 0 becomes true may happen at most 1 time in any 1000 ms.` and the Rule `count(rise(eq(BUTTON, 0)), 1000, 0)` as `BUTTON is 0 becomes true may happen at most 0 times in any 1000 ms.`
11. THE Renderer SHALL render the Rule `respond(rise(eq(BUTTON, 0)), 0.0000005, eq(LED, 1))` as `Within 0.0000005 ms after BUTTON is 0 becomes true, LED is 1 must be true.` and the Rule `hold(fall(eq(LED, 0)), 2.5, eq(LED, 1))` as `After LED is 0 becomes false, LED is 1 must stay true for 2.5 ms.`

### Requirement 3: Sentence Parser

**User Story:** As a teacher, I want a sentence that is not an exact template to be rejected with a reason, so that a typo never turns into a different rule.

#### Acceptance Criteria

1. WHEN the Sentence_Parser is given a string equal to the Canonical_Sentence of a valid Rule (a Rule that meets Requirement 1, criteria 2 to 7), THE Sentence_Parser SHALL return that Rule and no Reason.
2. IF the Sentence_Parser is given a string that is not the Canonical_Sentence of any valid Rule, THEN THE Sentence_Parser SHALL return a Reason and no Rule, never a different Rule, and SHALL return without throwing for every string, including the empty string.
3. THE Sentence_Parser SHALL match the input exactly as written: no case folding, no trimming or collapsing of whitespace, no Unicode normalization, no spelling correction, no synonym, no default value and no correction of singular or plural (`1 times` and `2 time` are rejected). As a result, a tab, CR, LF, non-breaking space, curly quote or non-ASCII digit anywhere in the input yields a Reason.
4. WHEN the Sentence_Parser returns a Reason, THE Sentence_Parser SHALL name in that Reason the zero-based character position P at which the input stops matching every template. P is the length of the longest prefix of the input that is also a prefix of the Canonical_Sentence of some valid Rule, so P equals the input length when the input ends early.
5. FOR ALL valid Rules r, `parse(render(r))` SHALL deep-equal r (round trip). Deep-equal means: the same fields with the same values, `of` members in the same order, Duration_Ms values equal as JavaScript numbers, and no field outside those listed in Requirement 1, criteria 2, 4 and 5 (a field set to `undefined` counts as an extra field).
6. FOR ALL strings s, IF `parse(s)` returns a Rule r, THEN `render(r)` SHALL equal s character for character (no silent change).
7. IF the input contains any of the following, THEN THE Sentence_Parser SHALL return a Reason and no Rule:
   - a number outside the range Requirement 1 allows: an `eq` value other than 0 or 1; an `above` value above 1022; a `below` value of 0 or above 1023; a `count` limit above 65,535; a Duration_Ms of 0, with an integer part above 9,999,999, or with more than 7 digits after the decimal point;
   - a break of another Requirement 1 limit: a Signal_Name longer than 32 characters, equal to `all` or `any`, or equal, ignoring case, to an entry of BANNED_WORDS; fewer than 2 or more than 8 members in `all of (...)` or `any of (...)`; Condition nesting deeper than 4;
   - a number in a form that criterion 4 of Requirement 2 does not produce, such as `0300`, `+5`, `-1`, `3e2`, `300.0`, `.5`, `5.`, `4,800` or `4_800`.
8. THE Sentence_Parser SHALL accept as a Signal_Name every string that Requirement 1, criterion 7 accepts, including words the templates use (such as `is`, `above`, `below`, `of`, `becomes`, `true`, `false`, `must`, `never`, `last`, `or`, `longer`, `Within` and `After`), SHALL reject with a Reason a Signal_Name that Requirement 1, criterion 7 rejects for equality with a BANNED_WORDS entry, and SHALL NOT check a Signal_Name against any Fixture. Requirement 6, criterion 2 handles unmapped signals.
9. WHEN the Sentence_Parser returns a Reason, THE Sentence_Parser SHALL name in that Reason the position P of criterion 4 and at least one Allowed_Character at P, or the end of the text when the end of the text is the only thing allowed at P, and SHALL keep the Reason within 1 to 200 characters. The Reason need not list every Allowed_Character. A run of consecutive characters may be named as a range, such as `0` to `3` or `a` to `z`, and every character in a named range SHALL be an Allowed_Character at P. The Reason SHALL copy no text from the input. The Reason result SHALL also carry P and the named characters (or the end of the text) as data fields equal to those the text names, so that a test can check them without reading the text.

### Requirement 4: Rules File

**User Story:** As a maker using the command line, I want one rules file format that holds either sentences or IR JSON, so that I can write rules by hand or by tool.

#### Acceptance Criteria

1. WHEN the Rules_File_Reader is given Rules_File text whose initial character that is not a space (U+0020), tab (U+0009), CR (U+000D) or LF (U+000A), after the steps of criteria 8 and 9, is `{`, THE Rules_File_Reader SHALL pass the whole text left by criterion 8, leading whitespace included, to the IR_Reader and SHALL return the IR_Reader's Rule_Set or Reasons unchanged.
2. WHEN the Rules_File_Reader is given Rules_File text that, after the steps of criteria 8 and 9, does not begin as stated in criterion 1, including text that is empty or holds only spaces, tabs, CRs and LFs, THE Rules_File_Reader SHALL split the text into lines at every LF, remove one CR at the end of each line, skip every line that is empty or holds only spaces and tabs, skip every line whose initial character is `#`, and parse every other line with the Sentence_Parser exactly as written, so that a line with a leading or trailing space or tab, or with `#` after a leading space or tab, is parsed and not skipped.
3. IF any parsed line yields a Reason, THEN THE Rules_File_Reader SHALL return one Reason for each failing line, in ascending line order, each beginning with the one-based line number of that line counted over every LF-separated line including skipped lines, each 1 to 200 characters long with the line number kept when the Sentence_Parser Reason is shortened, and SHALL return no Rule_Set.
4. IF every parsed line yields a Rule and the number of Rules is 0 or greater than 32, THEN THE Rules_File_Reader SHALL return a Reason that states the number of Rules found and the allowed range of 1 to 32, and SHALL return no Rule_Set.
5. WHEN every parsed line yields a Rule, the number of Rules is from 1 to 32 inclusive, and no two Rules have the same Canonical_Sentence, THE Rules_File_Reader SHALL return a Rule_Set whose Rules are in line order, with the i-th Rule taken from the i-th parsed line.
6. IF every parsed line yields a Rule and two or more parsed lines yield Rules with the same Canonical_Sentence, THEN THE Rules_File_Reader SHALL return a Reason that names each repeated sentence and the one-based line numbers of the lines that hold it, together with the Reason of criterion 4 when that criterion also applies, and SHALL return no Rule_Set.
7. THE Rules_File_Reader SHALL take the Rules_File text as a string, SHALL do no file input or output, and SHALL return a Rule_Set or Reasons without throwing for every string input.
8. WHEN the Rules_File text begins with the code unit U+FEFF, THE Rules_File_Reader SHALL remove that one code unit before any other step, including the length check of criterion 9. A U+FEFF at any later position, including a second one at the start, SHALL stay in the text. Line numbers of criteria 3 and 6 SHALL count the lines of the text left by this step, so the line that held the removed U+FEFF is line 1.
9. IF the text left by criterion 8 is longer than 65,536 UTF-16 code units, THEN THE Rules_File_Reader SHALL return exactly one Reason that states the limit of 65,536 UTF-16 code units, SHALL pass nothing to the IR_Reader, SHALL parse no line, and SHALL return no Rule_Set.

### Requirement 5: Durations in Cycles

**User Story:** As a firmware checker, I want every rule window measured in whole CPU cycles, so that timing never depends on rounding or on the host clock.

#### Acceptance Criteria

1. THE Rule_Compiler SHALL compute Window_Cycles as Duration_Ms × Clock_Rate / 1000 using exact integer arithmetic on the decimal value of Duration_Ms (as defined in Requirement 1, criterion 6) and on Clock_Rate, by a method that `design.md` names. The result SHALL be exact for every Duration_Ms that Requirement 1 accepts and every Clock_Rate that is a positive integer, including results above 2^53 − 1, with no floating-point rounding.
2. WHEN `fixture.clockHz` is `undefined` or `null`, THE Rule_Compiler SHALL use the Clock_Rate 16,000,000, the same default that `EmulatorBridge.create` applies with `fixture.clockHz ?? 16_000_000`. Otherwise THE Rule_Compiler SHALL use the `fixture.clockHz` value as given. Because `validateFixture` rejects `clockHz: null`, the `null` case is reached only by functions that take a Fixture without calling `validateFixture` (decision OQ1).
3. IF a Rule's Window_Cycles is not an integer, THEN THE Rule_Compiler SHALL mark the Rule with the `CannotCheck` reason `window not a whole number of cycles`. This covers every Window_Cycles greater than 0 and less than 1, because Duration_Ms > 0 and Clock_Rate > 0 make every integer Window_Cycles at least 1.
4. IF Clock_Rate is not a number that is an integer greater than 0 (for example 0, a negative value, 16,000,000.5, `NaN`, `Infinity`, or a non-number value), THEN THE Rule_Compiler SHALL mark every Rule that has a Duration_Ms with the `CannotCheck` reason `clock rate is not a whole number of hertz`, SHALL NOT also mark that Rule under criterion 3, and SHALL return without throwing.
5. WHEN Clock_Rate is 16,000,000, THE Rule_Compiler SHALL give 4,800,000 Window_Cycles for 300 ms, 1,600 for 0.1 ms, and 1 for 0.0000625 ms.
6. WHILE a Rule is marked with a `CannotCheck` under this requirement, THE Rule_Checker SHALL report no Violation for that Rule in any Run, and THE Rule_Checker SHALL keep checking every Active_Rule of the same Rule_Set.
7. WHEN Clock_Rate is 16,000,000, THE Rule_Compiler SHALL mark Rules with the Duration_Ms 0.0001 ms (1.6 cycles), 0.0000001 ms (0.0016 cycles) and 9,999,999.9999999 ms (159,999,999,999.9984 cycles) with `window not a whole number of cycles`, and SHALL give 159,999,984,000 Window_Cycles for 9,999,999 ms with no mark.
8. THE Rule_Compiler SHALL give each Rule at most one `CannotCheck` entry under this requirement, and SHALL give no `CannotCheck` entry under this requirement to a `never` Rule, because a `never` Rule has no Duration_Ms.

### Requirement 6: Signal Binding and Pin Kinds

**User Story:** As a student, I want a rule that names a missing or wrong pin to come back as COULDN'T TELL, so that the checker never guesses a pin's value.

#### Acceptance Criteria

1. WHEN a Rule_Set and a Fixture are compiled, THE Rule_Compiler SHALL return a Rule_Checker and a list of every Signal_Name the Rule_Set references, for use as `CampaignConfig.checkerSignals`. The list SHALL be in Rule_Set order and, within one Rule, in the order the Signal_Names appear in that Rule's Canonical_Sentence. Each Signal_Name SHALL appear once, at its earliest appearance. The list SHALL include the Signal_Names of Rules that carry a compile-time `CannotCheck` mark.
2. IF a Rule references a Signal_Name that does not equal the `signal` of any pin in `fixture.pins` by exact, case-sensitive string comparison, THEN THE Rule_Compiler SHALL mark the Rule with the `CannotCheck` reason `signal <S> is not mapped to a pin`, where <S> is the Signal_Name as written in the Rule, once for each distinct unmapped Signal_Name in that Rule.
3. IF an `eq` Condition names an Analog_Input, THEN THE Rule_Compiler SHALL mark the Rule with the `CannotCheck` reason `<S> is an analog input; use above or below`, once for each distinct such Signal_Name in that Rule.
4. IF an `above` or `below` Condition names a Digital_Input or an Output_Pin, THEN THE Rule_Compiler SHALL mark the Rule with the `CannotCheck` reason `<S> is not an analog input`, once for each distinct such Signal_Name in that Rule.
5. IF a Rule references a Signal_Name that equals the `signal` of two or more pins in `fixture.pins` by exact, case-sensitive string comparison, THEN THE Rule_Compiler SHALL mark the Rule with the `CannotCheck` reason `signal <S> is mapped to more than one pin`, once for each distinct such Signal_Name in that Rule, and SHALL apply neither criterion 3 nor criterion 4 to that Signal_Name. As a result, each distinct Signal_Name of a Rule gets at most one reason under criteria 2 to 5.
6. THE Rule_Compiler SHALL accept an `eq` Condition on a Signal_Name that is mapped to exactly one pin, which is a Digital_Input or an Output_Pin, and SHALL add no `CannotCheck` mark for that Condition.
7. WHEN the Rule_Checker is called with `stepIndex` 0 in any Run, THE Rule_Checker SHALL return in `cannotCheck` one entry `{ rule, reason }` for each distinct pair of Rule and compile-time reason from criteria 2 to 5 and Requirement 5, where `rule` is the Canonical_Sentence. Entries SHALL be in Rule_Set order. Within one Rule, the criteria 2 to 5 entries SHALL come in the order their Signal_Names appear in the Canonical_Sentence, followed by any Requirement 5 entry. These entries SHALL be returned in the same outcome as any Violation reported at that call.
8. WHILE a Rule carries a compile-time mark under criteria 2 to 5 or Requirement 5, THE Rule_Checker SHALL report no Violation for that Rule at any call. When at least one Active_Rule exists, the Rule_Checker SHALL return, at every call, the same `violation` (rule and cycle, or `null`) as a Rule_Checker compiled from only the Active_Rules, in their Rule_Set order, against the same Fixture. When no Active_Rule exists, it SHALL return `violation: null` at every call.
9. WHEN a valid Rule_Set is compiled against a Fixture that `validateFixture` accepts, THE Rule_Compiler SHALL return without throwing. This includes a Rule_Set in which every Rule carries a compile-time mark.
10. WHEN the Rule_Checker is called with `stepIndex` greater than 0, THE Rule_Checker SHALL return no `cannotCheck` entry for any reason of criteria 2 to 5 or Requirement 5.
11. IF the Rule_Compiler is given a value that is not a valid Rule_Set under Requirement 1, or a Fixture that `validateFixture` rejects, THEN THE Rule_Compiler SHALL return a Reason that names the rejected input (the Rule_Set, with the JSON path of the offending value written as Requirement 1, criterion 9 states, or the Fixture, with the `kind` of the error that `validateFixture` returns), SHALL copy no string value, no unlisted field name and no `message` or `signal` text of the `validateFixture` error into that Reason, SHALL return no Rule_Checker and no Signal_Name list, and SHALL return without throwing.

### Requirement 7: What the Monitor Sees

**User Story:** As a maker, I want the checker to judge each pin from the same data the emulator recorded, so that a verdict can be traced back to recorded events.

#### Acceptance Criteria

1. WHEN the Rule_Checker reads the `stepIndex` 0 observation, THE Rule_Checker SHALL take the Initial_State value of each referenced Output_Pin from the `OutputEvent` for that signal with `cycle` 0 that comes earliest in that observation's `outputEvents` list. This event is the bridge's cycle-0 snapshot (fact F1). `EmulatorBridge._build` step 9 builds one cycle-0 event for every Output_Pin. `advance()` prepends the snapshot on its initial call. `runOne` passes that Step's `outputEvents` in the `stepIndex` 0 observation. The bridge records every later `OutputEvent` after an instruction has run, so those events have `cycle` ≥ 1.
2. IF the `stepIndex` 0 observation carries no `OutputEvent` with `cycle` 0 for a referenced Output_Pin (for example, under a `bridgeFactory` test double that emits no snapshot), THEN THE Rule_Checker SHALL use `"input"` as that pin's Initial_State value. Every ATmega328P I/O pin is an input after reset, the bridge's pin shadow starts at `"input"`, and the real bridge reads its snapshot before any instruction runs, so the snapshot value is also `"input"`.
3. WHEN an observation carries an `OutputEvent` for a referenced Output_Pin, THE Rule_Checker SHALL set that pin's value to the event `value` (0, 1 or `"input"`) from the event `cycle` on. An `OutputEvent` for a signal that no Rule in the Rule_Set references SHALL leave every Rule_Checker outcome unchanged.
4. THE Rule_Checker SHALL set the Initial_State value of a Digital_Input to its Inactive_Level: 1 when the Active_Level is `"low"` or absent, and 0 when it is `"high"`. THE Rule_Checker SHALL then set it to the `value` of each Rest_Event for that signal in the `stepIndex` 0 observation. A Rest_Event is an applied digital input whose `gremlinId` is `"rest"`. The Gremlin_Engine generates Rest_Events at `cycle` 0, and the bridge applies them with `appliedCycle` 0, before any instruction runs.
5. THE Rule_Checker SHALL learn a Rest_State of `"active"` only from its Rest_Event, and SHALL NOT read the Fixture field `restState` to set any Initial_State.
6. WHEN an observation carries an applied digital input (an entry with a `value` field) that is not a Rest_Event, for a referenced Digital_Input, THE Rule_Checker SHALL change that pin's value at the entry's `appliedCycle`: to 0 for `value` 0, to 1 for `value` 1, and to the pin's Inactive_Level for `value` `"release"`. This includes Gremlin events applied at `appliedCycle` 0.
7. THE Rule_Checker SHALL set the Initial_State value of an Analog_Input to the Fixture pin's `restLevel` when the pin has one, and to 512 otherwise.
8. WHEN an observation carries an applied analog input (an entry with an `analog` field) for a referenced Analog_Input, THE Rule_Checker SHALL change that pin's value to the entry's integer `analog` value (0 to 1023) at the entry's `appliedCycle`.
9. THE Rule_Checker SHALL use `appliedCycle`, and not the scheduled `cycle`, as the cycle of every input change.
10. THE Rule_Checker SHALL model a Digital_Input by its external state, as stated in criteria 4 to 6. THE Rule_Checker SHALL NOT change that value based on the level the firmware reads. A released pin with no pull-up reads 0 in the firmware while the Rule_Checker holds the Inactive_Level, and Requirement 11, criterion 2 covers that case.
11. WHEN two or more changes to the same signal share one cycle, THE Rule_Checker SHALL resolve that signal's value at that cycle as Requirement 8, criterion 9 states.

### Requirement 8: Conditions and Edges

**User Story:** As a firmware checker, I want conditions judged on the settled state of each cycle, so that the order of events inside one cycle cannot change a verdict.

#### Acceptance Criteria

1. THE Rule_Checker SHALL define Settled_State(c), for every integer c from 0 to the end-of-run `observation.cycle` of the Run, as the Initial_State changed by every `OutputEvent` with `cycle` ≤ c and every applied input that is not a Rest_Event with `appliedCycle` ≤ c. The Rule_Checker SHALL evaluate Conditions only on the Initial_State and on Settled_States, so that changes that cancel out within one cycle have no effect. The cycle-0 output snapshot (fact F1) and the Rest_Events are already part of the Initial_State (Requirement 7, criteria 1 and 4).
2. THE Rule_Checker SHALL treat `eq(S, v)` as true in a state exactly when the value of S in that state is the number v, where S is a Digital_Input or an Output_Pin whose value is 0 or 1.
3. THE Rule_Checker SHALL treat `above(S, n)` as true exactly when the integer value of S is greater than n, and `below(S, n)` as true exactly when the integer value of S is less than n. Both are therefore false when the value equals n. For example, at value 512, `above(S, 512)` and `below(S, 512)` are false, while `above(S, 511)` and `below(S, 513)` are true.
4. THE Rule_Checker SHALL evaluate every member of an `all` or `any` Condition on the same state. It SHALL treat `all` as true when every member is true, and `any` as true when at least one member is true.
5. THE Rule_Checker SHALL record an Occurrence of `rise(C)` at cycle c when C is false in the preceding state and true in Settled_State(c). It SHALL record an Occurrence of `fall(C)` at cycle c when C is true in the preceding state and false in Settled_State(c). The preceding state is Settled_State(c − 1) for c ≥ 1 and the Initial_State for c = 0. So an Occurrence at cycle 0 happens only when an applied input that is not a Rest_Event, with `appliedCycle` 0, changes the truth value of C.
6. THE Rule_Checker SHALL record at most one Occurrence of one Edge per cycle. It SHALL record no Occurrence at cycle c when C has the same truth value in Settled_State(c) as in the preceding state of criterion 5, even when referenced signals change at cycle c.
7. FOR ALL reorderings of changes to different signals that share one cycle, and FOR ALL ways to split the changes of one cycle across consecutive observations as fact F3 allows, THE Rule_Checker SHALL give the same Settled_States and the same Occurrences (confluence). Changes to one signal at one cycle keep the order of criterion 9.
8. IF an Output_Pin S has the value `"input"` in a state, THEN THE Rule_Checker SHALL treat both `eq(S, 0)` and `eq(S, 1)` as false in that state. A change from `"input"` to 1 is then a rise of `eq(S, 1)`, and a change from 0 to `"input"` is a fall of `eq(S, 0)`.
9. IF two or more changes to one signal share one cycle (`OutputEvent`s with the same `cycle`, or applied inputs that are not Rest_Events with the same `appliedCycle`), THEN THE Rule_Checker SHALL give that signal, in Settled_State at that cycle, the value of the change that comes last in Application_Order.

### Requirement 9: Rule Form Semantics

**User Story:** As a student, I want each rule form to have one exact meaning in cycles, so that a BROKE trace points at the cycle that broke it.

#### Acceptance Criteria

1. IF C is true in Settled_State(c) for at least one cycle c ≥ 0, THEN THE Rule_Monitor for `never(C)` SHALL report a Violation at the lowest such c.
2. IF an Occurrence of E at cycle t is unmet, meaning C is false in Settled_State(c) for every c with t ≤ c ≤ t + W, where W is the Rule's Window_Cycles, THEN THE Rule_Monitor for `respond(E, d, C)` SHALL report a Violation at cycle t + W for the unmet Occurrence with the lowest t + W. An Occurrence is met when C is true at any c in that range, including c = t and c = t + W. Each Occurrence is judged on its own window, even when its window overlaps the window of another Occurrence. W is the same for every Occurrence of one Rule, and Requirement 8, criterion 6 allows at most one Occurrence of E per cycle. The lowest t + W is therefore the lowest t, and two unmet Occurrences can never tie.
3. IF, for some Occurrence of E at cycle e, more than k Occurrences of E have cycles in the range e − W + 1 to e inclusive, where W is the Rule's Window_Cycles and cycles below 0 hold no Occurrence, THEN THE Rule_Monitor for `count(E, d, k)` SHALL report a Violation at the lowest such e. When k is 0, that cycle is the cycle of the earliest Occurrence of E in the Run, whatever the value of W.
4. IF, for some Occurrence of E at cycle t, C is false in Settled_State(c) for some c with t ≤ c ≤ t + D − 1, where D is the Rule's Window_Cycles, THEN THE Rule_Monitor for `hold(E, d, C)` SHALL report a Violation at the lowest such c over all Occurrences of E. If C is false at c = t, the Violation is at t. A later Occurrence of E inside an earlier range adds its own range and does not shorten the earlier one.
5. IF C is true in Settled_State(c) for every c with s ≤ c ≤ s + L − 1, where L is the Rule's Window_Cycles and s is a span start (s = 0 when C is true in Settled_State(0), otherwise the cycle of an Occurrence of `rise(C)`), THEN THE Rule_Monitor for `notLongerThan(C, d)` SHALL report a Violation at cycle s + L for the lowest such s, whatever the value of C in Settled_State(s + L). A true span of exactly L cycles is therefore a Violation and a true span of L − 1 cycles is not, which matches the template wording `must never last d ms or longer` and `checkLedTimeout` (`ev.cycle >= onCycle + maxOnCycles`).
6. WHEN the Rule_Checker reports a Violation, THE Rule_Checker SHALL set `Violation.rule` to the Canonical_Sentence of the violated Rule and `Violation.cycle` to the cycle stated in criteria 1 to 5. That cycle is always one of: 0; the `cycle` of an `OutputEvent`; the `appliedCycle` of an applied input; an Occurrence cycle; or an Occurrence cycle or span start plus Window_Cycles. It SHALL NOT be derived from `observation.cycle`.
7. WHEN the end-of-run call arrives, THE Rule_Checker SHALL report no Violation and add no `CannotCheck` entry for an open window. An open window is one of these:
   - a `respond` Occurrence with t + W > `observation.cycle` and C false at every c from t to `observation.cycle`;
   - a `notLongerThan` span with s + L > `observation.cycle` and C true at every c from s to `observation.cycle`;
   - a `hold` range with t + D − 1 > `observation.cycle` and C true at every c from t to `observation.cycle`.

   Requirement 11, criterion 1 still applies to the Rule. Requirement 12, criterion 1 does not count an open window as a Trigger.
8. WHEN the end-of-run call arrives, THE Rule_Checker SHALL report a Violation at a cycle v from criteria 1 to 5 only if v ≤ `observation.cycle`. This includes a `respond` Violation with t + W equal to `observation.cycle`, a `notLongerThan` Violation with s + L equal to `observation.cycle`, and a `hold` Violation at a cycle c ≤ `observation.cycle` even when t + D − 1 > `observation.cycle`.
9. THE Rule_Monitor of each Active_Rule SHALL report at most one Violation per Run, at the lowest Violation cycle that criteria 1 to 5 give for that Rule in that Run.

### Requirement 10: Incremental Checker Contract

**User Story:** As the project owner, I want the checker to work Step by Step yet give the same answer as reading the whole trace, so that Step sizes cannot change a verdict.

#### Acceptance Criteria

1. THE Rule_Checker SHALL be a value of the `Checker` type in `src/engine/checker.ts`, SHALL process the observations of a Run in call order (which is ascending `observation.cycle` order), and SHALL keep state only between calls of the same Run.
2. WHEN the Rule_Checker is called with `stepIndex` 0, THE Rule_Checker SHALL discard all state from earlier calls before it reads the observation. This includes the state of an earlier Run whose calls stopped at a returned Violation with no end-of-run call, which is what `runOne` does.
3. WHEN the Rule_Checker is called with an observation whose `endOfRun` is false and whose `cycle` is X, THE Rule_Checker SHALL treat every cycle c with 0 ≤ c ≤ X − 1 as a Final_Cycle and SHALL NOT treat cycle X as a Final_Cycle, because an input applied at cycle X arrives in the next observation (fact F3).
4. THE Rule_Checker SHALL treat a Violation of an Active_Rule at cycle v (the cycle stated in Requirement 9, criteria 1 to 5) as reportable at a call exactly when cycle v is a Final_Cycle at that call and Requirement 11, criterion 6 does not exclude the Violation. The same rule applies to every Rule_Form, so a `notLongerThan` Violation at s + L waits until cycle s + L is a Final_Cycle.
5. WHEN the end-of-run call arrives with `observation.cycle` X, THE Rule_Checker SHALL report an open `respond` window as a Violation only when X ≥ t + W, and an open `notLongerThan` span as a Violation only when X ≥ s + L. THE Rule_Checker SHALL compare the limit with X and not with Run_Cycles, because X can be a few cycles above Run_Cycles (fact F6).
6. WHEN one or more Active_Rules have a reportable Violation at one call, THE Rule_Checker SHALL return exactly one Violation. That Violation SHALL be the one with the lowest cycle, and on equal cycles the one whose Rule is earlier in Rule_Set order. Because every cycle below a Final_Cycle is also a Final_Cycle, this Violation SHALL equal the lowest (cycle, Rule_Set position) Violation of the whole Run under Requirement 9 and Requirement 11, criterion 6.
7. WHEN no Active_Rule has a reportable Violation at a call, THE Rule_Checker SHALL return `violation: null`. This includes every call of a Run in which every Rule of the Rule_Set has a compile-time `CannotCheck`.
8. THE Rule_Checker SHALL return outcomes that pass the `callChecker` validation of fact F7. Each outcome SHALL be an object whose `violation` is `null` or `{ rule, cycle }`, where `rule` is a non-empty string and `cycle` is an integer with 0 ≤ `cycle` ≤ `observation.cycle`. The outcome's `cannotCheck` SHALL be absent or an array of `{ rule, reason }` string pairs. THE Rule_Checker SHALL return without throwing for every observation sequence that `runOne` produces.
9. THE Rule_Checker SHALL return the same Violation (rule and cycle), or none, for a Run under every split of the Run's data that `runOne` can produce. Two splits are compared when they carry the same output events, applied inputs, diagnostics and end-of-run cycle. A split that `runOne` can produce has these properties:
   - `stepIndex` runs 0, 1, 2, … and the non-end-of-run `cycle` values strictly ascend.
   - Each observation's output events have cycles above the previous observation's `cycle`, except the cycle-0 snapshot of fact F1.
   - Each applied input has an `appliedCycle` from the previous observation's `cycle` (0 at `stepIndex` 0) to `cycle` − 1.
   - The sequence ends with an end-of-run call that carries the last `cycle` and empty lists, or it is cut after the call that returns a Violation.
10. WHEN the Rule_Checker is called with an observation whose `endOfRun` is true and whose `cycle` is X, THE Rule_Checker SHALL treat every cycle c with 0 ≤ c ≤ X as a Final_Cycle.
11. IF the Rule_Checker receives a call that breaks the call order, THEN THE Rule_Checker SHALL throw an Error that names the mismatch, so that `callChecker` reports a `checker-error` and the Campaign stops, and SHALL return no Violation from that call. A call breaks the call order when any of these holds:
    - Its `stepIndex` is neither 0 nor one more than the previous call's `stepIndex`.
    - It is a non-end-of-run call whose `cycle` is not above the previous call's `cycle`.
    - It is an end-of-run call whose `cycle` is below the previous call's `cycle`.
    - It follows an end-of-run call and its `stepIndex` is not 0.

### Requirement 11: Run-Level COULDN'T TELL Reasons

**User Story:** As a maker, I want the checker to say when one run could not judge a rule, so that a missing check is never reported as a pass.

#### Acceptance Criteria

1. WHEN the Rule_Checker is called with `observation.endOfRun` true, THE Rule_Checker SHALL return, for each Active_Rule of form `respond`, `count`, `hold` or `notLongerThan` whose Window_Cycles is greater than `observation.cycle`, one `CannotCheck` entry `{ rule, reason }` with `reason` equal to `run shorter than the rule window`, except for the Rule whose Violation that same call returns.
2. WHEN an observation carries a Floating_Diagnostic and no earlier observation of the same Run carried one, THE Rule_Checker SHALL return in the outcome of that call one `CannotCheck` entry for every Active_Rule, in Rule_Set order, whether or not the Rule's Conditions reference the floating signal and whether or not that outcome carries a Violation. The `reason` SHALL be `input <S> was read while floating`, where S is the `signal` of the Floating_Diagnostic that comes earliest in Application_Order in that Run, or `an input was read while floating` when that `signal` is not a valid Signal_Name under Requirement 1, criterion 7. Each Active_Rule SHALL get at most one such entry per Run, even when later diagnostics in the Run name other signals.
3. IF an observation carries a `floating-input` diagnostic whose `signal` is not the `signal` of any Digital_Input in the Fixture, THEN THE Rule_Checker SHALL return the same outcome at that call and at every later call of the Run as it returns when that diagnostic is absent. Fact F8 means only a `bridgeFactory` test double can produce such a diagnostic.
4. THE Rule_Checker SHALL write every `CannotCheck` reason it returns as a Reason of 1 to 200 characters, and SHALL set the `rule` of every `CannotCheck` entry it returns to the Canonical_Sentence of the Rule concerned.
5. THE Rule_Checker SHALL return, for an Active_Rule in a Run, no `CannotCheck` entry other than those of criteria 1 and 2, so that a Run in which the Trigger of that Rule did not occur adds no `CannotCheck` entry for that reason (Requirement 12 handles it at Campaign level).
6. IF a Run's observations carry a Floating_Diagnostic for signal S, with d the lowest diagnostic `cycle` for S in that Run, THEN THE Rule_Checker SHALL report, in that Run, a Violation of an Active_Rule whose Conditions reference S only when the Violation cycle is below d, SHALL report no other Violation of that Rule in that Run, and SHALL keep checking every Active_Rule whose Conditions do not reference S.

### Requirement 12: Campaign-Level Trigger Check

**User Story:** As a student, I want a rule whose trigger never happened to come back as COULDN'T TELL, so that a rule that was never exercised is not reported as HELD.

#### Acceptance Criteria

1. THE Trigger_Evaluator SHALL count a Trigger of a Rule in a Run only when the Rule's window fits in that Run, where W, D and L are the Rule's Window_Cycles: for `respond`, an Occurrence of its `trigger` Edge at a cycle t with t + W ≤ `endCycle`; for `hold`, an Occurrence of its `after` Edge at a cycle t with t + D − 1 ≤ `endCycle`; for `count`, any Occurrence of its `edge`; for `notLongerThan`, a span start s (as defined in Requirement 9, criterion 5) with s + L ≤ `endCycle`, or a span start s whose span ends in the Run, meaning its Condition is false in Settled_State(c) for some c with s < c ≤ `endCycle`. THE Trigger_Evaluator SHALL give `never` Rules no Trigger, so that `never` Rules are never Untriggered_Rules.
2. THE Trigger_Evaluator SHALL be a pure function of a Rule, a Fixture and one `RunResult` that returns whether the Trigger occurred in that Run. It SHALL read only `outputEvents`, `appliedInputs` and `endCycle` of the `RunResult`, SHALL compute Window_Cycles from the Fixture as Requirement 5 states, SHALL build the Initial_State as Requirement 7, criteria 1, 2, 4 and 7 state (cycle-0 `OutputEvent`s, `"input"` for an Output_Pin with none, Inactive_Level changed by `appliedInputs` with `gremlinId` `"rest"`, and `restLevel` or 512), SHALL build Settled_States and Occurrences as Requirement 8 states, SHALL consider cycles 0 to `endCycle` inclusive, SHALL return not occurred for a Rule that is not an Active_Rule against that Fixture, SHALL leave its arguments unchanged, and SHALL return without throwing for every `RunResult` that `runOne` produces.
3. WHEN the Untriggered_Rule function is given a Rule_Set, a Fixture and a list of 0 or more completed `RunResult`s, THE Rule_Compiler SHALL return the Canonical_Sentence of each Active_Rule that has a Trigger and for which the Trigger_Evaluator reports no Trigger in every `RunResult` of the list. The sentences SHALL come in Rule_Set order, each at most once, and SHALL exclude every Rule that is not an Active_Rule. For an empty list, the result SHALL be every Active_Rule other than `never` Rules.
4. THE `computeVerdict` function SHALL accept one new optional `VerdictInput` field that lists Untriggered_Rules as Canonical_Sentences, next to the existing fields `requestedRuns`, `runs`, `finished`, `unmappedSignals` and `unsupportedPeripherals`, and SHALL leave the types and meanings of those existing fields unchanged.
5. IF `finished` is true, no `RunResult` in `runs` has a Violation, and the Untriggered_Rule field lists at least one sentence, THEN THE `computeVerdict` function SHALL return `COULDN'T TELL` and SHALL NOT return `HELD`. The reason SHALL be built by the existing method: parts joined with `"; "`, then cut at 200 UTF-16 code units without leaving half of a surrogate pair. The parts SHALL include one part per distinct listed sentence, with the exact text `Rule "<sentence>" could not be checked: trigger never happened in <R>`, where <R> is the Run_Count_Phrase for N (`1 run` when N is 1, `N runs` otherwise). These parts SHALL be in field order, after every part from a Run `CannotCheck` entry and before the unmapped-signal, unsupported-peripheral, short-run and no-gremlin-event parts.
6. IF `finished` is true, some `RunResult` in `runs` has a Violation, and the Untriggered_Rule field lists at least one sentence, THEN THE `computeVerdict` function SHALL return `BROKE` with a `trace` deep-equal to the one it returns without the field. Its `unchecked` list SHALL be the existing entries in their existing order, followed by one entry `{ rule: <sentence>, reason: "trigger never happened in <R>" }` per listed sentence in field order, where <R> is the Run_Count_Phrase for N. An entry SHALL be skipped when its `rule` and `reason` both equal an entry already in `unchecked`.
7. IF the Trigger of an Active_Rule occurred in at least one completed Run, THEN THE Untriggered_Rule function SHALL omit that Rule, however many other completed Runs lacked the Trigger (for example, 1 quiet Run out of 64). THE `computeVerdict` function SHALL then add no trigger reason for that Rule, so that a Run without the Trigger cannot by itself make the Campaign `COULDN'T TELL`.
8. THE `computeVerdict` function SHALL keep the order `BROKE`, then `COULDN'T TELL`, then `HELD`, SHALL return exactly one Verdict per call and per Campaign, and SHALL use only the existing strings `VERDICT_BROKE`, `heldText(n)` and `VERDICT_COULDNT_TELL`.
