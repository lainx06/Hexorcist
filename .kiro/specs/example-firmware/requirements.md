# Requirements Document

## Introduction

This feature adds small example programs for Hexorcist. Each Example is one ATmega328P sketch written twice: a Buggy_Sketch with one planted Bug and a Fixed_Sketch that differs from it in as few lines as possible. Each Example also ships a Fixture, a rules file of Canonical_Sentences, and campaign settings. The app and the video use them to show `BROKE` on the buggy build and `HELD` on the fixed build.

The Core_Examples are `crosswalk` (the hero example), `garage` (the scene with a cartoon cat) and `heartbeat`. The Optional_Example is `heater`. It is the earliest to cut: when scope must shrink, `heater` goes before any Core_Example. All `heater` work comes after the three Core_Examples pass, and nothing else depends on `heater`.

This spec builds on the code in `src/engine/` and changes none of it. It adds files under `examples/` (the Example directories, the kept Build_HEX files and `examples/README.md`), one build script under `scripts/`, one npm script in `package.json`, one `.gitignore` line in a later task, and new test files. It adds no package. The UI, the cat art and the video are out of scope; this spec only supplies the data they read. Test results from this spec are evidence, not proof.

### Facts from the current code

`design.md` quotes each of these from the source. They are listed here so the criteria below can refer to them.

- F1. Fixture shape. `Fixture` is `{ clockHz?: number; pins: FixturePin[] }`, and `FixturePin` is `DigitalFixturePin | AnalogFixturePin` (`src/engine/types.ts`). A digital pin has `signal`, `port` (`"B" | "C" | "D"`), `bit` (0 to 7), `direction` (`"output" | "input"`), and, on input pins only, optional `activeLevel` (`"low" | "high"`, default `"low"`) and `restState` (`"released" | "active"`, default `"released"`). An analog pin has `kind: "analog"`, `channel` (integer 0 to 5) and optional `restLevel` (integer 0 to 1023, default 512).
- F2. Fixture validation. `validateFixture(fixture)` in `src/engine/fixture.ts` returns `null` when it accepts the Fixture and a `BridgeError` otherwise. It also rejects an analog pin whose channel N shares port C bit N with a digital pin.
- F3. Gremlins. `GremlinSpec` is `{ id: string; params?: Record<string, number | { min: number; max: number }> }` (`src/engine/gremlins/catalogue.ts`). It has no field that picks a pin. `resolveParams(spec)` returns a `ResolvedGremlin` or an `EngineError`. The six Gremlins and their targets are: `masher`, `bouncer` and `stuck` pick one pin from every Digital_Input (`ctx.eligible.digital`); `dropout` picks one pin from the Digital_Inputs with `restState: "active"` (`ctx.eligible.restActive`); `spike` and `drifter` pick one Analog_Input (`ctx.eligible.analog`). A Gremlin with no eligible pin skips with reason `no-target-pin` (`digital.ts`, `analog.ts`).
- F4. Releases. Every digital Gremlin can emit a Release: `masher` emits one after each Press, `bouncer` alternates Press and Release, `stuck` releases when the release lands inside the Run, and `dropout` starts with a Release (`digital.ts`).
- F5. Released-pin level. `_presentReleased` in `src/engine/emulator-bridge.ts` presents a released input at HIGH when the firmware enabled the pull-up and at LOW when it did not (`port.setPin(pin.bit, state === PinState.InputPullUp)`). The PIN read hook emits a `floating-input` Diagnostic when a released input with no pull-up is covered by a PIN register read.
- F6. Checker view of a Release. The Rule_Checker and the Trigger_Evaluator value a Release at the pin's Inactive_Level (`values[s] = a.value === "release" ? kind.inactiveLevel : a.value` in `src/engine/rules/trace.ts`). Inactive_Level is 1 for `activeLevel` `"low"` or absent and 0 for `"high"` (`kindOf` in `src/engine/rules/bind.ts`).
- F7. Floating reads become CannotCheck. When an observation carries a `floating-input` Diagnostic for a Digital_Input, the Rule_Checker adds a CannotCheck with reason `input <SIGNAL> was read while floating` for every Active_Rule (`src/engine/rules/rule-checker.ts`, step 3).
- F8. Run length. At end of Run the Rule_Checker adds a CannotCheck with reason `run shorter than the rule window` for every Active_Rule with a window whose cycle limit is above the end cycle (`rule-checker.ts`, step 7). 1 ms is 16,000 cycles at 16 MHz.
- F9. Triggers. `triggerOccurred` returns `false` for every `never` Rule, and `untriggeredRules` skips `never` Rules (`src/engine/rules/trigger.ts`). A `respond` Rule's Trigger counts only when its earliest Occurrence `c` has `c + limit <= endCycle`. A `notLongerThan` Rule's Trigger counts when a span of its Condition starts and either ends inside the Run or lasts to `spanStart + limit <= endCycle`.
- F10. Verdict. `computeVerdict` in `src/engine/verdict.ts` returns `BROKE` when any Run has a Violation. Otherwise it returns `COULDN'T TELL` when any Run carries a CannotCheck, when any Rule is an Untriggered_Rule, when a checker signal is unmapped, when fewer than N Runs completed, or when no event with a `gremlinId` other than `"rest"` exists in any Run. Otherwise it returns `HELD` with text `heldText(n)`, which is `No violation found in ${n} runs of this gremlin set. Not a proof.`
- F11. Rules file. `readRulesFile(text)` in `src/engine/rules/rules-file.ts` reads one Canonical_Sentence per line, skips blank lines and lines that begin with `#`, and returns `{ ok: true, ruleSet }` or `{ ok: false, reasons }`. The templates in `render.ts` are: `<C> must never happen.`, `Within <ms> ms after <E>, <C> must be true.`, `<E> may happen at most <n> time(s) in any <ms> ms.`, `After <E>, <C> must stay true for <ms> ms.`, `<C> must never last <ms> ms or longer.`, where `<E>` is `<C> becomes true` or `<C> becomes false`, and `all`/`any` render as `all of (<C>, <C>)`.
- F12. Campaign wiring. `buildCampaignConfig(ruleSet, fixture, rest)` in `src/engine/rules/config-builder.ts` returns `{ ok: true, config }` or `{ ok: false, reasons }`. `runCampaign(config)` in `src/engine/campaign.ts` returns a `CampaignResult` (`runsCompleted`, `requestedRuns`, `violatingRunIndex`, `verdict`) or a `CampaignError`.
- F13. Rest_Events come from the event list. `generateWithPrng` in `src/engine/event-list.ts` adds one Rest_Event per `restState: "active"` pin at cycle 0. `EmulatorBridge.create(hex, fixture, events)` adds none.
- F14. Wired peripherals. `EmulatorBridge.supports` reports `gpio`, `external-interrupt`, `pin-change-interrupt`, `timer0`, `timer1`, `timer2` and `adc` as wired. The USART is not wired.
- F15. Committed builds contain brand text. `fixtures/blink_button/build/blink_button.ino.elf` holds 9 case-insensitive matches of a board brand name in its debug data. The `.hex`, `.eep` and `.with_bootloader.*` files in that folder hold none.

### Facts used by the rulings below

These were read from the working tree for this revision. `design.md` quotes each one with its file path and line range.

- `runCampaign(config)` is `createCampaign(config)` followed by one `runSlice(N)`, and returns `SliceProgress.result` (`campaign.ts`). `SliceProgress.runs` holds every completed `RunResult`. `CampaignResult` holds no Run_Results; its `BROKE` verdict holds one `BrokeTrace` (`runIndex`, `runSeed`, `eventList`, `outputEvents`, `violation`) for the lowest violating Run (`types.ts`, `verdict.ts`).
- With default settings a Campaign stops after the earliest Run that has a Violation (`isFinished` and the slice loop in `campaign.ts`; the default is `true` in `resolveSettings`). `runOne` stops a Run at the Step whose observation reported the Violation (`break` in the step loop), so that Run's `outputEvents` end at that Step.
- Every Run calls the generator of every `gremlinSet` entry in listed order (`for (const entry of resolved)` in `generateWithPrng`). A Gremlin adds no event to a Run only when it skips or when every event it draws lands at or past `runCycles`.
- A `RunResult` holds `eventList` (every generated event, applied or not), `appliedInputs` (digital and analog entries in application order, each with its `gremlinId`) and `outputEvents` (`types.ts`). The bridge adds one `outputEvents` entry per output pin at cycle 0 and one entry each time an output pin's state changes, checked after every instruction (`emulator-bridge.ts`, `advance`).
- `pressValue(pin)` is 1 for `activeLevel: "high"` and 0 for `"low"` or absent (`src/engine/gremlins/pins.ts`).

## Glossary

- **Example**: One directory `examples/<id>/`, where `<id>` is `crosswalk`, `garage`, `heartbeat` or `heater`.
- **Example_Set**: All Example directories under `examples/`.
- **Core_Example**: The `crosswalk`, `garage` or `heartbeat` Example.
- **Optional_Example**: The `heater` Example. It is the earliest to cut, and all work on it comes after the Core_Examples pass (Requirement 1, criteria 12 and 13).
- **Sketch**: One `.ino` file of an Example: `buggy/buggy.ino` or `fixed/fixed.ino`.
- **Variant**: `buggy` or `fixed`.
- **Sketch_Directory**: `examples/<id>/<variant>/`.
- **Buggy_Sketch**: `examples/<id>/buggy/buggy.ino`. It contains the Example's Bug.
- **Fixed_Sketch**: `examples/<id>/fixed/fixed.ino`. It is the Buggy_Sketch with the Bug fixed.
- **Bug**: The one planted defect of an Example, described in that Example's requirement.
- **Build_Folder**: The temporary directory `<Sketch_Directory>/build/` that the Build_Script's compile command writes. The Build_Script removes it after each compile, and no Build_Folder under `examples/` is committed (OI-1).
- **Build_HEX**: The kept file `examples/<id>/<variant>/<variant>.hex`, that is `buggy/buggy.hex` or `fixed/fixed.hex` in an Example. The Build_Script writes it as a byte-for-byte copy of `<Sketch_Directory>/build/<variant>.ino.hex` after a passing compile. The user compiles and commits it (OI-1).
- **Example_Fixture**: The file `examples/<id>/fixture.json`. It holds one Fixture as JSON.
- **Example_Rules**: The file `examples/<id>/rules.txt`. It holds Canonical_Sentences, one per line.
- **Example_Meta**: The file `examples/<id>/meta.json`. It holds the Example's title, story, Timing_Note and Campaign settings.
- **Timing_Note**: The `timingNote` field of an Example_Meta (Requirement 22).
- **Examples_README**: The file `examples/README.md` (Requirement 21, criteria 13 and 14).
- **Build_Script**: The new file `scripts/build-examples.mjs`, run with `npm run examples:build`.
- **Example_Tests**: The new vitest test files this spec adds, in `tests/examples/` (Requirement 15, criterion 11; D19). The campaign runner helper takes an optional `clock` argument. The test files supply the clock, and the helper files never read a clock (D21).
- **Phase_F**: The whole implementation of this spec, that is, all tasks of `tasks.md`. The build-script acceptance within it is CP1 (task 2) (Requirement 7, criterion 13; D18).
- **Brand_Check**: The Example_Tests test that scans the `.ino`, `.json`, `.txt` and `.hex` files under `examples/` for Board_Brand_Names (Requirement 18).
- **Board_Brand_Name**: One of the eight words that Requirement 18, criterion 3 lists: `Arduino`, `Genuino`, `Uno`, `Nano`, `Mega`, `Leonardo`, `Duemilanove` and `Diecimila`. Matching is whole word and ignores case (Requirement 18, criterion 4). The text `ATmega328P` holds no Board_Brand_Name match (D15).
- **Brand_Matcher**: The function that the Brand_Check and the Examples_README check of Requirement 21, criterion 14 use to find Board_Brand_Name matches in a text. It lives in an Example_Tests file or a shared test helper (D15).
- **BANNED_WORDS**: The exported list in `src/engine/copy-rules.ts`. This document does not write the words out.
- **Phase_Constant**: A Sketch constant that sets how long a visible output state lasts, such as a light phase or a toggle interval. Debounce and timeout constants are not Phase_Constants. The `garage` auto-close delay of 300 ms is a Phase_Constant (Requirement 9, criterion 10; D11).
- **Door_State**: The `garage` Sketch's internal record of the door: `open`, `closing`, `closed` or `opening`. The fixture has no door-position input, so `design.md` fixes the starting Door_State, every Door_State change, and the Output_Levels of `MOTOR_CLOSE`, `MOTOR_OPEN` and `LAMP` that each Door_State shows, so that Scripted_Run tests can check Door_State from Output_Edges (D11, D12).
- **CLOSE_Press**: A change of the `garage` Digital_Input `CLOSE` to its Press_Value 0. A Press event on `CLOSE` while `CLOSE` is already at 0 is not a change, so it is not a CLOSE_Press (D13).
- **Per_Run_Odds**: For the `garage` Buggy_Sketch Example_Campaign, the chance, which `design.md` computes, that one Run holds a Violation of the `garage` Rule (D12).
- **Miss_Chance**: For the `garage` Buggy_Sketch Example_Campaign with N Runs, the chance, which `design.md` computes from the Per_Run_Odds, that none of the N Runs holds a Violation (D12). It is an estimate; the seeded Example_Campaign decides the verdict (Requirement 15, criterion 16).
- **Example_Campaign**: A Campaign whose config `buildCampaignConfig` builds from the Rule_Set that `readRulesFile` reads from the Example_Rules, the Fixture parsed from the Example_Fixture, and the Build_HEX, `gremlinSet`, `campaignSeed`, `runs` and `runCycles` of the Example_Meta. It is run by `createCampaign(config)` followed by one `runSlice(N)`, which is the body of `runCampaign`, so that the test gets both the `CampaignResult` and the N Run_Results (Requirement 15, criterion 4). Each Example_Campaign is run once per build, with no second pass (D1).
- **Scripted_Run**: One run of a Build_HEX on `EmulatorBridge.create(hex, fixture, events)` with a hand-written event list, advanced to the Example_Meta `runCycles`. The one exception is the Buggy_Sketch Minimal_Bug_Input Scripted_Run used to measure a Violation_Span (Requirement 21, criterion 2), which advances to the Replay_End (D9). In every Scripted_Run, every event cycle is below the Example_Meta `runCycles` (Requirement 16, criterion 5). Its observations go to the Rule_Checker compiled from the Example_Rules and Example_Fixture, in the same order and shape `runOne` in `src/engine/campaign.ts` uses. In the Scripted_Run that advances to the Replay_End, the Violation used for the verdict checks and for the span is the earliest one, at cycle v, and v must be below the Example_Meta `runCycles` (Requirement 14, criterion 3, unchanged).
- **Replay_Run**: One run of a Build_HEX on a new `EmulatorBridge.create(hex, fixture, events)`, where `hex` and `fixture` are those of an Example_Campaign and `events` is the `eventList` of one of its Run_Results in the same order, advanced from cycle 0 to the Replay_End. It records Output_Edges. It uses no snapshot. A Replay_Run is used only to measure a Violation_Span (Requirement 21) and is not a pass of an Example_Campaign. Campaign Runs keep the Example_Meta `runCycles` (D6).
- **Replay_End**: The cycle at which a Replay_Run stops, and at which the Buggy_Sketch Minimal_Bug_Input Scripted_Run used to measure a Violation_Span (Requirement 21, criterion 2) stops: the Example_Meta `runCycles` plus 32,000 cycles (2 ms at 16 MHz past the campaign's run end), counted from cycle 0 of that run (D6, D9).
- **Output_Edge**: One `outputEvents` entry `{ signal, value, cycle }` recorded by the bridge: one per output pin at cycle 0, then one each time an output pin's state changes.
- **Output_Level**: The level of an output at cycle t: the `value` of the latest Output_Edge of that output with cycle at or below t, with every Output_Edge at cycle t applied.
- **Conflicting_Outputs**: A pair of outputs of one Example that a Fixed_Sketch never sets to 1 at the same cycle. Requirement 21, criterion 8 lists the `crosswalk` pairs (D14); `design.md` fixes the `garage` pairs within that criterion.
- **Violation_Span**: For one Violation at cycle v, the number of cycles from v to the end that Requirement 21, criterion 3 defines for the Rule's template.
- **Campaign_Duration**: The wall-clock time in ms that an Example_Test measures around the call that runs a Fixed_Sketch Example_Campaign. It is a measurement for the test output and the task report only (Requirement 15, criteria 10 to 14; D3). The time that decides the report and stop actions is the standalone `npm run bench:examples` time of the Fixed_Sketch campaign; a time measured inside Vitest is printed for information only (D24).
- **Minimal_Bug_Input**: The hand-written event list for an Example that `design.md` gives as the smallest input it knows of that makes the Buggy_Sketch violate a Rule.
- **Single_Input**: For an Example, one ordinary user action written as a Scripted_Run event list. For a Digital_Input, this is one Press followed by one Release on the same pin after an Ordinary_Hold. For an Analog_Input, this is one Analog_Event with a value from 0 to 899. `design.md` fixes the pin, cycle and value per Example (OI-2).
- **Ordinary_Hold**: The time from a Single_Input Press to its Release: at least 1 cycle and at most 200 ms (3,200,000 cycles at 16 MHz). `design.md` fixes the value per Example (OI-2).
- **Double_Press_Window**: For `crosswalk`, the span of time after one REQUEST Press inside which a second REQUEST Press triggers the Bug. It is given in ms in the `crosswalk` Example_Meta.
- **Recorded_Acceptance_Values**: For a Buggy_Sketch Example_Campaign, the literals `violatingRunIndex`, `trace.violation.cycle` and the event count, written into the test after it passes for the initial time. The event count is the number of entries in the `BROKE` trace's `eventList` whose `gremlinId` is not `"rest"`. Output_Edges are not counted (OI-8).
- **Diagnostic**: An entry of an observation's `diagnostics` list, emitted by the EmulatorBridge (F5).
- **Floating_Diagnostic**: A Diagnostic with `kind: "floating-input"`.
- **Gremlin catalogue**: The Gremlin definitions and `resolveParams` in `src/engine/gremlins/catalogue.ts` (F3).
- **Press_Value**: The value `pressValue(pin)` returns for a Digital_Input: 0 for `activeLevel` `"low"` or absent, 1 for `"high"`.
- **agent**: The AI coding assistant that carries out the tasks of this spec.
- **committed file**: A file that `git ls-files` lists when a task starts.
- **Fixture**, **validateFixture**: As in F1 and F2.
- **GremlinSpec**, **Gremlin**, **Gremlin_Set**, **Checker**, **Violation**, **Digital_Input**, **Analog_Input**, **Active_Level**, **Rest_State**, **Rest_Event**, **Rest_Level**, **Press**, **Release**, **Analog_Event**, **Run**, **Run_Index**, **Run_Cycles**, **Campaign**, **Campaign_Seed**, **Run_Result**, **Verdict**: As defined in the `gremlin-engine` spec.
- **Canonical_Sentence**, **Condition**, **Renderer**, **Rules_File_Reader**, **Reason**, **Rule**, **Rule_Set**, **Rule_Compiler**, **Rule_Checker**, **Active_Rule**, **Trigger**, **Trigger_Evaluator**, **Untriggered_Rule**, **CannotCheck**, **Inactive_Level**, **Occurrence**, **Window_Cycles**, **Campaign_Config_Builder**: As defined in the `rule-compiler` spec.

4. FOR EACH Example, THE Example SHALL contain the Build_HEX files `buggy/buggy.hex` and `fixed/fixed.hex`, at these paths relative to `examples/<id>/`, written by the Build_Script and compiled and committed by the user. (Decision OI-1. The kept path is outside the Build_Folder, because Build_Folders are not committed. Interpretation accepted in D5.)
5. THE committed files under `examples/` SHALL be exactly: for each Example, the five files of criterion 3 and the two Build_HEX files of criterion 4; and the Examples_README. No Build_Folder and no `.elf`, `.map`, `.eep` or other compile output under `examples/` SHALL be committed. (Decision OI-1.)
6. THE agent SHALL write no Build_HEX and no file inside any Build_Folder, and SHALL leave every compile and every commit of a Build_HEX to the user (Requirement 7, criterion 6; Requirement 19, criteria 3 and 4).
7. THE `.gitignore` SHALL gain an entry that ignores `examples/**/build/`. This entry is a deliverable of a later task in `tasks.md`, and THE agent SHALL add it only in that task (Requirement 19, criterion 1).
8. THE agent SHALL leave every file under `fixtures/blink_button/build/`, the `.elf` file included, unchanged (Decision OI-1, F15).
9. WHERE the Optional_Example is included, THE Example_Set SHALL contain `examples/heater/` with the files of criteria 3 and 4.
10. IF the agent finds that an Example cannot meet a criterion of this document within the planned tasks, THEN THE agent SHALL drop the Optional_Example before any Core_Example and SHALL report the drop to the user, naming the criterion that could not be met and the reason.
11. IF a Core_Example cannot meet a criterion of this document after the Optional_Example has been dropped, THEN THE agent SHALL stop, keep the Core_Example and its files, report the Example, the criterion and the reason, and wait for the user's decision (Requirement 19, criterion 6).
12. THE `tasks.md` SHALL place every task that creates or changes a file under `examples/heater/` or a test of the `heater` Example after the tasks in which the Buggy_Sketch and Fixed_Sketch Example_Campaign tests of all three Core_Examples pass and their Recorded_Acceptance_Values are written into those tests. (User ruling on `heater`.)
13. THE Core_Example files, the Core_Example tests, the Build_Script, the Brand_Check, the file validation tests of Requirement 17 and every shared test helper SHALL work the same whether or not `examples/heater/` exists. No Core_Example test SHALL read a file under `examples/heater/`, and the Build_Script, the Brand_Check and the file validation tests SHALL run over the Examples that exist. (User ruling: "If it is cut, nothing else may depend on it.")

### Requirement 2: Sketch source

**User Story:** As a maker, I want the example sketches to be plain, short programs for the ATmega328P, so that I can read them and they run in the emulator.

#### Acceptance Criteria

1. THE Sketch SHALL be plain C++ for the ATmega328P at 16 MHz that uses only the core library and includes no other library. A Sketch meets this when the Build_Script's compile command (Requirement 7, criterion 2) compiles it and the Sketch has no `#include` directive naming a header outside the core library that this command provides.
2. THE Sketch SHALL use only the peripherals that `EmulatorBridge.supports` reports as wired (F14): GPIO, external and pin-change interrupts, timer0, timer1, timer2 and the ADC. A Sketch meets this when it has no `Serial` call and does not access any other register of the USART or of any other peripheral missing from that list.
3. THE Sketch SHALL set every Phase_Constant to a value from 50 ms to 300 ms. Both ends count as inside the range. Each Phase_Constant SHALL be declared as a named constant at file scope, and its value SHALL be given in ms.
4. THE Sketch SHALL read and drive each Example signal on the port and bit, or the ADC channel, that the Example_Fixture gives for that signal. A Sketch meets this when it configures each Example_Fixture output as an output on that output's port and bit, configures each Digital_Input as an input on that input's port and bit (with the pull-up setting that Requirement 3 sets), and reads each Analog_Input only from that input's ADC channel.
5. THE Sketch SHALL begin with a comment that names the Example id, says whether the build is buggy or fixed, and lists the pin map, in the style of `fixtures/blink_button/blink_button.ino`. The comment SHALL be a block of `//` lines placed before any code line. It SHALL contain the Example id, exactly one of the words `buggy` or `fixed`, and one line for each Example_Fixture signal. Each of those lines SHALL give the signal name, the port letter and bit (for example `PD2`) or the ADC channel, and the direction or kind.
6. THE Fixed_Sketch SHALL differ from the Buggy_Sketch only in the lines that remove the Bug and in the comment lines that name the build as fixed. A pair of Sketches meets this when every line in the line diff between them (the diff that `design.md` shows, per Requirement 20, criterion 4) is either a header comment line from criterion 5 or a line of the Bug fix. Every Phase_Constant value and every pin assignment SHALL be the same in both Sketches. (User constraint: minimal diff between buggy and fixed builds.)
7. THE Sketch SHALL configure, read or drive no pin and no ADC channel that the Example_Fixture does not map. A pin the fixture does not map cannot be checked, and a rule on such a pin can only get the verdict `COULDN'T TELL`.
8. IF the Bug of an Example, or the fix of that Bug, cannot be written using only the wired peripherals of criterion 2 and the pins of the Example_Fixture, THEN THE agent SHALL stop and report the Example, the peripheral or pin it would need, and the reason. THE agent SHALL leave the constraint unchanged (see Requirement 19, criterion 6).

### Requirement 3: No input read while floating

**User Story:** As a student, I want every example input to have a defined level, so that a verdict never rests on a floating pin.

#### Acceptance Criteria

1. FOR EACH Digital_Input of an Example, THE Sketch SHALL configure the pin with `INPUT_PULLUP`, or THE Example_Fixture SHALL give the pin `restState: "active"` so that a Rest_Event drives the pin. (User constraint, as given: no floating inputs.)
2. WHERE the Example_Meta `gremlinSet` contains `masher`, `bouncer`, `stuck` or `dropout`, each of which can emit a Release on a Digital_Input (F4), THE Buggy_Sketch and THE Fixed_Sketch SHALL each configure with `INPUT_PULLUP`, before that Sketch's earliest read of the pin, every Digital_Input that the Gremlin can target (F3: every Digital_Input for `masher`, `bouncer` and `stuck`; every Digital_Input with `restState: "active"` for `dropout`), so that a Release leaves the pin HIGH on the chip (F5). (Derived from F4, F5 and F7. Accepted by the user under OI-3: "Every input a gremlin can touch uses INPUT_PULLUP.")
3. THE Example_Fixture SHALL give every Digital_Input an `activeLevel` of `"low"` or no `activeLevel`, so that the Rule_Checker's value for a Release is the Inactive_Level 1 (F6), which equals the HIGH level the chip reads on a released pin with the pull-up enabled (F5). (Derived from F5 and F6. Accepted by the user under OI-4.)
4. WHERE the Example_Meta `gremlinSet` contains `dropout`, THE Example_Fixture SHALL give `restState: "active"` to each Digital_Input that `design.md` names as a `dropout` target for that Example, and to at least one Digital_Input, because `dropout` targets only such inputs and otherwise skips with reason `no-target-pin` (F3). The `garage` `gremlinSet` holds no `dropout` (Requirement 9, criterion 3).
5. WHEN an Example_Campaign of the Buggy_Sketch Build_HEX or of the Fixed_Sketch Build_HEX finishes, THE Example_Campaign SHALL hold, in every Run_Result it produced, no Floating_Diagnostic and no CannotCheck with reason `input <SIGNAL> was read while floating` (F7).
6. WHEN a Scripted_Run of any Build_HEX has advanced to its end cycle, which is the Example_Meta `runCycles`, or the Replay_End for the Scripted_Run of Requirement 21, criterion 2 (D9), THE Rule_Checker SHALL have received no observation that carries a Floating_Diagnostic and SHALL report no CannotCheck with reason `input <SIGNAL> was read while floating` (F7).
7. IF a Run_Result of an Example_Campaign or the observations of a Scripted_Run hold a Floating_Diagnostic, THEN THE Example_Tests SHALL fail with a message that names the Example id, the build (`buggy` or `fixed`), the Run_Index or the Scripted_Run name, and the floating signal, and THE agent SHALL stop and report under Requirement 19, criterion 6, and leave this constraint unchanged.

### Requirement 4: Example Fixture

**User Story:** As a developer, I want each example's pin map in a Fixture file that the engine accepts, so that the pin map is fixture data and not code.

#### Acceptance Criteria

1. THE Example_Fixture SHALL be JSON text that parses without a syntax error to one JSON object that is a `Fixture` (F1) and for which `validateFixture` returns `null`.
2. THE Example_Fixture SHALL map every signal named in the Example_Rules to exactly one pin entry, and SHALL give no two pin entries the same `signal` value, compared case-sensitively.
3. THE Example_Fixture SHALL have no `clockHz` field, or a `clockHz` equal to the integer 16,000,000.
4. THE Example_Fixture SHALL contain exactly the signals listed in the Example's requirement (Requirements 8 to 11), each with the direction or kind given there. Each Digital_Input SHALL be a digital pin entry with `direction: "input"`. Each output SHALL be a digital pin entry with `direction: "output"`. Each Analog_Input SHALL be a pin entry with `kind: "analog"` on the ADC channel given there. The Example_Fixture SHALL contain no pin entry for a signal not listed there.
5. THE Example_Fixture SHALL give each pin entry only `signal` and the fields that F1 lists for its kind. On a digital pin entry, `bit` SHALL be an integer from 0 to 7, `direction` SHALL be exactly `"input"` or `"output"`, and `activeLevel` and `restState` SHALL appear only on `direction: "input"` entries, within the limits of Requirement 3, criteria 1 to 4. A digital pin entry SHALL have no `kind` field, so `kind: "digital"` is not written, and an analog pin entry SHALL have no `direction` field. (Decision D16: "The F1 omission stays out of the fixtures.") (Derived from F1 and F2: `validateFixture` does not check `direction` on digital pins, does not check that `bit` is an integer, and does not reject unknown fields. A misspelled field name would be ignored and its default used.)
6. THE Example_Fixture SHALL give no two digital pin entries the same `port` and `bit` pair. (Derived from F2: `validateFixture` checks shared physical pins only between an analog channel N and port C bit N.)
7. THE Example_Fixture SHALL place every digital pin entry on a general I/O pin of the ATmega328P at 16 MHz: port `"B"` bits 0 to 5, port `"C"` bits 0 to 5, or port `"D"` bits 0 to 7. (Derived. On the ATmega328P, port B bits 6 and 7 carry the 16 MHz crystal, port C bit 6 is the reset pin, and port C bit 7 does not exist. `validateFixture` accepts bits 0 to 7 on every port (F2).)

### Requirement 5: Example rules

**User Story:** As a student, I want each example's rules written as the plain-English sentences the app shows, so that what I read is what gets checked.

#### Acceptance Criteria

1. WHEN `readRulesFile` reads the Example_Rules text, THE Rules_File_Reader SHALL return `{ ok: true, ruleSet }` with no Reason, and `ruleSet` SHALL hold exactly one Rule per line of the Example_Rules, in file order (F11). (User constraint, as given; the count and order clause is added for testability.)
2. WHEN `render` is called on the k-th Rule of the `ruleSet` that `readRulesFile` returns for an Example_Rules text, THE Renderer SHALL return `{ ok: true, sentence }` where `sentence` equals the k-th line of the Example_Rules character for character, with no leading or trailing spaces or tabs on either side (round trip).
3. WHEN `compileRuleSet(ruleSet, fixture)` (`src/engine/rules/compile.ts`) is called with the `ruleSet` read from the Example_Rules and the Fixture parsed from the Example_Fixture, THE Rule_Compiler SHALL return `{ ok: true, compiled }` with no Reason.
4. WHEN `analyzeRuleSet(ruleSet, fixture)` (`src/engine/rules/bind.ts`) is called with the same `ruleSet` and Fixture, THE Rule_Compiler SHALL return a plan in which every entry of `plans` has `active: true` and an empty `marks` list (zero compile-time CannotCheck entries), so that every Rule is an Active_Rule.
5. THE Example_Rules SHALL be UTF-8 text with no byte-order mark and with LF line endings. It SHALL contain each Canonical_Sentence line given in the Example's requirement (Requirements 8 to 11) exactly once, and no other line, blank line or comment line. A single line break after the last line SHALL be allowed and SHALL NOT count as a blank line.
6. IF `readRulesFile` returns `{ ok: false, reasons }` for an Example_Rules, or `compileRuleSet` returns `{ ok: false, reasons }`, or `analyzeRuleSet` returns a `plans` entry with `active: false`, THEN THE Example_Tests SHALL fail and show every Reason or compile-time CannotCheck with its line number or Rule index, and THE agent SHALL stop and report the Example, the line and the Reason, and SHALL leave the Canonical_Sentence line, the Example_Fixture and the test unchanged (Requirement 19, criterion 6).
7. THE Example_Rules SHALL use only the five Canonical_Sentence templates of F11 for every line. (User constraint: only the five sentence templates.)

### Requirement 6: Example Meta

**User Story:** As a teacher, I want each example to carry its own title, story and campaign settings, so that the app runs it the same way every time.

#### Acceptance Criteria

1. THE Example_Meta SHALL be JSON text that parses to one JSON object with the fields `title` (string), `story` (string), `timingNote` (string, Requirement 22), `gremlinSet` (array of at least one GremlinSpec entry), `runCycles` (integer), `campaignSeed` (integer) and `runs` (integer). It SHALL have no other field, except the Double_Press_Window fields of criterion 8 in the `crosswalk` Example_Meta.
2. THE Example_Meta `story` SHALL be one line of text with no line break, meaning no `\n` and no `\r` character, and SHALL be 1 to 300 characters long.
3. THE Example_Meta `title` SHALL be 1 to 80 characters long and SHALL contain no `\n` and no `\r` character.
4. WHEN `resolveParams` is called on each `gremlinSet` entry, THE Gremlin catalogue SHALL return a `ResolvedGremlin` and no `EngineError`.
5. THE Example_Meta `runCycles` SHALL be an integer from 8,000,000 to 16,000,000 inclusive, which is 0.5 s to 1.0 s of simulated time at 16 MHz. `design.md` sets the value per Example within this range, except for `heartbeat`, whose value criterion 6 and Requirement 10, criterion 8 fix.
6. THE Example_Meta `runCycles` SHALL be at least the largest Window_Cycles of the Example's Rules, so that no Run gets the CannotCheck `run shorter than the rule window` (F8). Window_Cycles is the Rule's ms value times 16,000. For `heartbeat` (two 600 ms Rules) `runCycles` SHALL be exactly 16,000,000 (Decision OI-7, confirmed in D3).
7. THE Example_Meta `campaignSeed` SHALL be an integer from 0 to 4,294,967,295 inclusive. `runs` SHALL be an integer from 1 to the per-Example upper bound that `design.md` states. For `heartbeat`, `runs` SHALL be exactly 24 (Decision OI-7 as amended by D3).
8. THE `crosswalk` Example_Meta SHALL give the Double_Press_Window (Requirement 8, criterion 3) as a start and an end in ms after the earlier REQUEST Press. Both SHALL be integers with 1 ≤ start < end and end × 16,000 < `runCycles`. `design.md` SHALL name the two fields.
9. THE Example_Meta `title`, `story` and `timingNote` SHALL contain no word of BANNED_WORDS and no Board_Brand_Name, matched as whole words in any letter case.
10. IF an Example_Meta does not parse as JSON, or any of its fields fails criteria 1 to 9 or Requirement 22, THEN THE Example_Tests SHALL fail with a message that names the Example id and each failing field, and SHALL start no Example_Campaign from that Example_Meta.

### Requirement 7: Build script

**User Story:** As the author, I want one command that compiles every example sketch and keeps only the HEX files, so that I can rebuild all HEX files and see at once if any build fails.

#### Acceptance Criteria

1. THE Build_Script SHALL be the file `scripts/build-examples.mjs`, written in plain Node with no new dependency, and `package.json` SHALL have the npm script `"examples:build"` that runs it.
2. WHEN the Build_Script runs, THE Build_Script SHALL compile every Sketch_Directory under `examples/` with the command `arduino-cli compile -b arduino:avr:uno --output-dir <dir>/build <dir>`, where `<dir>` is that Sketch_Directory. A Sketch_Directory is each `examples/<id>/buggy/` and `examples/<id>/fixed/` that exists at the time of the run. This includes `examples/heater/` only when the Optional_Example is included. The Build_Script SHALL compile them in ascending order of Example id, with `buggy` before `fixed` within each Example, and SHALL pass each `<dir>` to the command as one argument, so that a path containing spaces compiles the same way as one without. (Command kept exactly as given; OI-9.)
3. WHEN a compile finishes, THE Build_Script SHALL print one line that names the Sketch_Directory and says whether the compile passed or failed, before it starts the next compile.
4. IF a compile fails, or `arduino-cli` cannot be started, THEN THE Build_Script SHALL delete `<dir>/build/` and every file in it (criterion 12), SHALL keep the existing Build_HEX of that Sketch_Directory unchanged, SHALL print the Sketch_Directory and the error output of that compile, SHALL go on to compile every remaining Sketch_Directory, SHALL print a closing summary with the number of passed compiles, the number of failed compiles and, for each failed compile, the Example id and Variant marked as not rebuilt, and SHALL exit with a non-zero exit code. (Decision D5: "when a compile fails, the build script deletes build/, keeps the old HEX, prints which examples were not rebuilt, and exits with a non-zero code.")
5. THE Build_Script SHALL be the only code, data or example file of this feature that contains the board name text of the compile command (OI-9).

Each signal SHALL be on its own port and bit, and the Example_Fixture SHALL hold no Analog_Input (Requirement 4, criterion 4).

THE `garage` Example_Rules SHALL contain exactly the one line `Within 20 ms after BEAM_CLEAR is 0 becomes true, MOTOR_CLOSE is 0 must be true.` `BEAM_CLEAR` 1 means the beam is clear and `BEAM_CLEAR` 0 means the beam is blocked. A Press on `BEAM_CLEAR` drives it to 0, its Press_Value (blocked). WHILE `MOTOR_CLOSE` is 1, WHEN `BEAM_CLEAR` flickers as in the `garage` Minimal_Bug_Input, THE `garage` Buggy_Sketch SHALL keep `MOTOR_CLOSE` at 1 for more than 20 ms after the Trigger, because the flicker defeats the Buggy_Sketch's debounce (the Bug). The criterion applies to every cycle c at which the Condition becomes true, including each one in the `garage` Minimal_Bug_Input and each one a Gremlin causes, whether or not `MOTOR_CLOSE` was 1 at cycle c.
7. THE `garage` Example_Meta `story` SHALL describe a cat passing through the beam and SHALL contain the words `cat` and `beam` as whole words in any letter case.
8. WHEN `CLOSE` receives a CLOSE_Press, THE `garage` Buggy_Sketch and THE `garage` Fixed_Sketch SHALL respond according to Door_State as follows (Decisions D12 and D13):
   - Door not closed. WHILE Door_State is not `closed`, `MOTOR_CLOSE` is 0 and `BEAM_CLEAR` is 1, a CLOSE_Press SHALL set `MOTOR_CLOSE` to 1 within the number of ms that `design.md` states for the `CLOSE` response (the `CLOSE` response time). That number SHALL be small enough that the Trigger of criteria 4 and 5 can fall while `MOTOR_CLOSE` is 1 with c + 320,000 at or below the Example_Meta `runCycles` (F9).

     - IF that Miss_Chance is at most 1%, THEN a CLOSE_Press while Door_State is `closed` SHALL do nothing: `MOTOR_CLOSE` and `MOTOR_OPEN` SHALL stay 0 and Door_State SHALL stay `closed` at every cycle from the CLOSE_Press to the next input event or the end of the Run, whichever comes earlier.
     - IF that Miss_Chance is above 1%, THEN the earlier behaviour SHALL apply: a CLOSE_Press while `MOTOR_CLOSE` is 0 and `BEAM_CLEAR` is 1 SHALL set `MOTOR_CLOSE` to 1 within the `CLOSE` response time, whatever the Door_State, `closed` included.
   - Not a CLOSE_Press. A Press event on `CLOSE` while `CLOSE` is already at its Press_Value 0 is not a change of `CLOSE`, so it is not a CLOSE_Press, and THE `garage` Sketch SHALL give it no response (D13).
9. THE `design.md` SHALL record, for the `garage` Buggy_Sketch Example_Campaign with `campaignSeed` 20261102 and N = 40, the recomputed Per_Run_Odds and Miss_Chance under the door-closed-does-nothing behaviour, the working that gives them, and which branch of criterion 8 it chose. The Example_Tests SHALL test the branch that `design.md` chose. (Decision D12.)
10. WHILE `BEAM_CLEAR` is 1, WHEN Door_State has been `open` for 300 ms (4,800,000 cycles at 16 MHz) with no Door_State change, THE `garage` Buggy_Sketch and THE `garage` Fixed_Sketch SHALL close the door by itself by setting `MOTOR_CLOSE` to 1 within the `CLOSE` response time of criterion 8 (auto-close). The 300 ms value SHALL be a Phase_Constant under Requirement 2, criterion 3, with the same value in both Sketches. (Decision D11.)
11. THE `garage` Example_Meta `story` SHALL say that the door closes by itself after 300 ms open, and SHALL contain the text `300 ms`. (Decision D11.)
12. THE `garage` Example_Meta `timingNote` SHALL say that the door closes by itself after 300 ms open and that this is demo timing. It SHALL contain the text `300 ms` and the word `demo` as a whole word in any letter case. `design.md` gives the text (Requirement 22, criterion 6). (Decision D11.)

The Example_Tests read the Run_Results from `SliceProgress.runs` (Requirement 15, criterion 4); with no Violation, the Fixed_Sketch Example_Campaign completes all N Runs (Requirement 13, criterion 2). "Each GremlinSpec in the Example_Meta `gremlinSet`" is the accepted reading of "every gremlin chosen in an example's fixture" (D5). (Kept by D2, pointing at the fixed build.)

COULDN'T TELL.`, near lines 91 to 118) returns `COULDN'T TELL` when any of these holds: a completed Run carries a CannotCheck (`run.cannotCheck`); a Rule is an Untriggered_Rule (`input.untriggeredRules`); a checker signal is not mapped to a pin (`input.unmappedSignals.length > 0`); a peripheral is named as unsupported (`input.unsupportedPeripherals.length > 0`, which `campaign.ts` always passes as an empty list); fewer Runs completed than requested (`runs.length !== input.requestedRuns`); or no Run's `eventList` holds an event whose `gremlinId` is not `"rest"` (`!runs.some((r) => r.eventList.some((e) => e.gremlinId !== "rest"))`). `design.md` quotes these lines.

### Requirement 21: Violations are not glitches

**User Story:** As a student, I want a `BROKE` to come from a fault that lasts, and fixed builds whose conflicting outputs never overlap, so that a one-cycle glitch never decides a verdict.

#### Acceptance Criteria

1. WHEN a Buggy_Sketch Example_Campaign returns `BROKE`, THE Example_Tests SHALL measure the Violation_Span of `trace.violation` on a Replay_Run of the `BROKE` trace's `eventList`, advanced to the Replay_End (D6), and SHALL expect the Violation_Span to be at least 16,000 cycles (1 ms of simulated time at 16 MHz), also when the Replay_End cuts the span. (User ruling, as given: "A buggy build's violation must last at least 1 ms of simulated time; the test asserts this and the report gives the span in cycles and ms.")
2. WHEN a Buggy_Sketch Minimal_Bug_Input Scripted_Run reports a Violation, THE Example_Tests SHALL measure the Violation_Span of the earliest Violation, at cycle v, from that Scripted_Run's Output_Edges, with the Scripted_Run advanced from cycle 0 to the Replay_End and the span measured to the Replay_End, and SHALL expect the Violation_Span to be at least 16,000 cycles, also when the Replay_End cuts the span. The Scripted_Run's event list is the one of Requirement 16, criterion 5, so every event cycle is below the Example_Meta `runCycles`, and v is below `runCycles` (Requirement 14, criterion 3). (Decision D9.)
3. THE Example_Tests SHALL measure each Violation_Span from Output_Levels, by Rule template, with v the Violation cycle and the measurement end M set to the Replay_End (the Example_Meta `runCycles` plus 32,000 cycles, counted from cycle 0) for both the Replay_Run of criterion 1 (D6) and the Scripted_Run of criterion 2 (D9). The span runs from v to the earlier of M and the earliest cycle after v at which the Rule's Condition `<C>` changes, which is, per template:
   - `<C> must never happen.`: the earliest cycle after v at which `<C>` is false.
   - `Within <ms> ms after <E>, <C> must be true.`: the earliest cycle after v at which `<C>` is true.
   - `<C> must never last <ms> ms or longer.`: the earliest cycle after v at which `<C>` is false.

   IF `<C>` does not change after v and before M, THEN the span SHALL end at M, and the span is cut by replay end, for the Replay_Run and for the Scripted_Run alike (D9). A span cut by the Replay_End SHALL still reach 16,000 cycles (criteria 1 and 2; D6: "If the Replay_Run end cuts the span, it still has to reach 16,000 cycles."; D9). Campaign Runs keep the Example_Meta `runCycles`; only the Replay_Run and the Scripted_Run of criterion 2 go past it (D6, D9). Every Condition that these spans watch in the Example_Rules of this spec names only outputs, so Output_Edges alone give the span. The Example_Rules of this spec use only these three templates. `design.md` SHALL fix the exact measurement, including whether each end cycle counts, and SHALL quote the Rule_Checker code that sets v for each of the three templates.
4. THE Example_Tests SHALL obtain the Output_Edges after the Violation of a `BROKE` trace from a Replay_Run, because `runOne` stops a Run at the Step whose observation reported the Violation, so the trace's `outputEvents` end at that Step. The Replay_Run uses the same Build_HEX, the same Example_Fixture and the trace's `eventList` in the same order, on a new bridge with no snapshot, advances from cycle 0 to the Replay_End (D6), and changes no file under `src/engine/`.
5. WHEN a Replay_Run is made, THE Example_Tests SHALL check that the leading Output_Edges of the Replay_Run, as many as the trace's `outputEvents` holds, equal the trace's `outputEvents` entry for entry. IF they differ, THEN the test SHALL fail and THE agent SHALL stop and report the Example, the index of the earliest differing entry and both entries.
6. WHEN a Violation_Span is measured, THE Example_Tests SHALL write one line to the test output that gives the Example id, the Rule's Canonical_Sentence, v, the Violation_Span in cycles and the Violation_Span in ms (cycles divided by 16,000, with the number of decimals that `design.md` fixes), and whether the span was cut by replay end. This line format applies to spans measured on a Replay_Run of criterion 1 and on a Scripted_Run of criterion 2 (D6, D9).
7. IF a Violation_Span is below 16,000 cycles, THEN the test SHALL fail, and THE agent SHALL stop and report the Example, the Rule, v, the Violation_Span in cycles and ms, whether the span was cut by replay end, and the `BROKE` trace or the Scripted_Run event list, leaving the test, the Rule and the Sketch unchanged. This criterion applies to every Example, `garage` included: a `garage` Violation_Span under 16,000 cycles (1 ms) stops the agent under Requirement 19, criterion 11. (Decision D16: "A garage span under 1 ms means stop and report.")
8. THE Conflicting_Outputs of `crosswalk` SHALL be exactly the six pairs (`CAR_GREEN`, `WALK`), (`CAR_YELLOW`, `WALK`), (`WALK`, `DONT_WALK`), (`CAR_GREEN`, `CAR_YELLOW`), (`CAR_GREEN`, `CAR_RED`) and (`CAR_YELLOW`, `CAR_RED`), and each of the six SHALL hold in the `crosswalk` Fixed_Sketch under criteria 9 and 10 (D14). The Conflicting_Outputs of `garage` SHALL be the pairs that `design.md` fixes, including at least (`MOTOR_CLOSE`, `MOTOR_OPEN`). `heartbeat` and `heater` each have one output and have no Conflicting_Outputs.
9. WHEN the Fixed_Sketch drives one output of a Conflicting_Outputs pair to 1, THE Fixed_Sketch SHALL already have driven the other output of that pair to 0 at an earlier cycle. (User ruling: "A fixed build turns every output off before turning another on, so conflicting outputs never overlap even for one cycle." Read per Conflicting_Outputs pair; reading accepted in D5.)
10. FOR EACH Conflicting_Outputs pair, THE Example_Tests SHALL check, in every Run_Result of the Fixed_Sketch Example_Campaign and in every Fixed_Sketch Scripted_Run, that there is no cycle at which the Output_Levels of both outputs are 1. A Fixed_Sketch Run_Result with no Violation holds its Output_Edges up to `runCycles`, so no Replay_Run is needed for this check.
11. IF the check of criterion 10 finds a cycle at which both outputs of a pair are 1, THEN the test SHALL fail with a message that names the Example, the Run_Index or Scripted_Run name, the pair and the earliest such cycle, and THE agent SHALL stop and report under Requirement 19, criterion 7.
12. THE Buggy_Sketch SHALL use the same off-before-on order as the Fixed_Sketch in every line that is not part of the Bug, because Requirement 2, criterion 6 limits the diff to the Bug-fix lines. (Derived.)
13. THE Examples_README `examples/README.md` SHALL exist and SHALL contain a note that the glitch-tolerant rule form is `<C> must never last 1 ms or longer.`, which is the template `<C> must never last <ms> ms or longer.` of F11 with `<ms>` set to 1. (User ruling: "Add a note to the README for examples that the glitch-tolerant rule form is '<C> must never last 1 ms or longer.'")
14. THE Example_Tests SHALL check that the Examples_README exists, contains the text `<C> must never last 1 ms or longer.`, and contains no Board_Brand_Name and no word of BANNED_WORDS, matched as whole words in any letter case. This is a separate test from the Brand_Check, whose scope Decision OI-1 limits to `.ino`, `.json`, `.txt` and `.hex` files. (Interpretation accepted in D5.)

### Requirement 22: Demo timing note

**User Story:** As a teacher, I want each example to say where its timings are shorter than on a real device, so that nobody mistakes demo timings for real ones.

#### Acceptance Criteria

1. THE Example_Meta SHALL hold a field `timingNote` whose value is a plain-English string that says where the Example's timings are compressed for the demo. (User ruling, as given: "Each meta.json carries a plain-English 'timingNote' field that says where timings are compressed for the demo, e.g. 'Demo timing: WALK phase 200 ms (a real crossing is much longer).'")
2. THE Example_Meta `timingNote` SHALL be non-empty after `String.prototype.trim`.
3. THE Example_Meta `timingNote` SHALL contain no word of BANNED_WORDS and no Board_Brand_Name, matched as whole words in any letter case (Requirement 6, criterion 9).
4. WHEN the file validation tests run, THE Example_Tests SHALL check that `timingNote` exists, is a string and is non-empty after `String.prototype.trim` (Requirement 17, criterion 8).
5. IF an Example_Meta has no `timingNote`, a `timingNote` that is not a string, or a `timingNote` that is empty after `String.prototype.trim`, THEN THE Example_Tests SHALL fail with a message that names the Example id and the field `timingNote`.
6. THE `design.md` SHALL give the `timingNote` text for each Example (Requirement 20, criterion 9).
